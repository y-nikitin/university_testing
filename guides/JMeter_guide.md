# Apache JMeter: довідник для Performance and Load Testing

> **Призначення.** Цей матеріал пояснює можливості Apache JMeter, будову тестового сценарію, способи запуску та аналізу результатів. Це **не готове рішення лабораторної роботи**: бізнес-сценарій, профілі навантаження, перевірки та висновки необхідно спроєктувати самостійно.

## 1. Що таке JMeter

**Apache JMeter** — інструмент для тестування продуктивності та створення навантаження. Він може надсилати паралельні HTTP-запити, виконувати сценарії від імені віртуальних користувачів, перевіряти відповіді, записувати час виконання та формувати статистику й графічні звіти.

Типова задача: оцінити, як REST API працює під невеликим, звичайним і підвищеним навантаженням. JMeter вимірює поведінку системи, але **не визначає автоматично причину** сповільнення сервера.

- **GUI mode:** конструювання сценаріїв, перевірка окремих запитів, налагодження.
- **CLI / non-GUI mode:** запуск реальних навантажувальних тестів без графічного інтерфейсу, запис результатів і побудова HTML Dashboard. Саме CLI рекомендується для навантажувальних прогонів.

Файл **`.jmx`** — XML-документ, у якому зберігається конфігурація Test Plan. Це **не JavaScript-скрипт**. Файл **`.jtl`** — журнал вимірювань окремих виконань запитів (зазвичай CSV, якщо залишено типові налаштування).

## 2. Як побудований Test Plan

У JMeter сценарій задається деревом елементів. Основні категорії:

| Елемент | Роль у сценарії |
|---|---|
| **Test Plan** | Кореневий контейнер тесту, глобальні параметри та змінні. |
| **Thread Group** | Кількість віртуальних користувачів (*threads*), швидкість їх запуску (*ramp-up*), ітерації або тривалість, поведінка при помилках. |
| **Sampler → HTTP Request** | Конкретний HTTP-запит: метод, URL/path, заголовки, query parameters, body. |
| **Config Element → HTTP Request Defaults** | Спільні значення для запитів: protocol, host, port тощо. |
| **Config Element → HTTP Header Manager** | HTTP-заголовки, наприклад `Content-Type: application/json`. |
| **Post Processor → JSON Extractor** | Дістає дані з JSON-відповіді для наступних кроків сценарію. |
| **Assertion → Response Assertion** | Перевіряє HTTP status code або вміст відповіді. |
| **Assertion → JSON Assertion** | Перевіряє JSON-структуру/поле та, за потреби, очікуване значення. |
| **Logic Controller** | Керує порядком, умовами, повтореннями чи групуванням дій. |
| **Timer** | Додає затримки між діями, якщо вони потрібні моделі користувача. |
| **Listener** | Відображає або зберігає результати вимірювань. |

**Приклад структури**, а не готовий сценарій для конкретного SUT:

```text
Test Plan
└── Thread Group
    ├── HTTP Request Defaults
    ├── HTTP Header Manager
    ├── HTTP Request: Create resource
    │   ├── Response Assertion
    │   └── JSON Extractor
    ├── HTTP Request: Read resource
    │   └── Response Assertion
    ├── HTTP Request: Update resource
    │   └── Response Assertion
    ├── View Results Tree
    └── Aggregate Report
```

**Порядок Samplers має значення:** коли наступний запит залежить від попереднього, необхідно передати отримані дані й обробити можливу невдачу попередньої операції. У великих навантажувальних запусках діагностичні Listener-и на кшталт **View Results Tree** варто вимикати: вони споживають пам’ять та ресурси генератора.

## 3. Virtual users і профіль навантаження

**Virtual User (VU)** у стандартній Thread Group відповідає потоку JMeter, який послідовно проходить сценарій. Ключові налаштування:

- **Number of Threads (users)** — скільки одночасних користувачів планується запустити.
- **Ramp-up Period** — протягом якого часу користувачі вводяться в навантаження. Наприклад, 20 користувачів за 10 секунд — це приблизно 2 нові потоки за секунду, а **не** 2 HTTP-запити за секунду.
- **Loop Count** — скільки разів один користувач повторює сценарій; `Infinite` означає повторення до завершення тесту.
- **Specify Thread lifetime / Duration** — обмеження часу виконання групи (залежно від обраного режиму Thread Group).
- **Action after a Sampler error** — що зробити після помилки: продовжити, почати наступну ітерацію, зупинити потік чи тест.

Кількість VUs **не дорівнює** requests per second. Фактичний request rate залежить від часу відповідей, кількості операцій у сценарії, пауз, ресурсів генератора та сервера.

### Типові профілі

| Профіль | Для чого використовують |
|---|---|
| **Baseline** | Початкова точка порівняння при невеликому навантаженні. |
| **Load** | Робота за помірного або поступово зростаючого навантаження. |
| **Stress** | Робота за значно вищого навантаження, за безпечних меж середовища. |
| **Spike** | Реакція на короткочасний різкий стрибок навантаження та повернення до меншого рівня. |

Для різних послідовних фаз навантаження можна застосовувати кілька Thread Groups із контрольованим розкладом або спеціальні плагіни. Наявність одного лише Ramp-up не означає, що тест уже реалізує повний багатоступеневий workload.

## 4. Динамічні дані та перевірки

Для пов’язаних запитів потрібна **кореляція**: зберегти значення, отримане в одному запиті, і використати в наступному.

Приклад: HTTP-відповідь містить `{"id": 42}`. JSON Extractor може отримати `$.id` у змінну `resourceId`, а наступний Sampler використає шлях:

```text
/resources/${resourceId}
```

Поширені елементи синтаксису:

| Синтаксис | Призначення |
|---|---|
| `${resourceId}` | Використати значення змінної JMeter. |
| `${__UUID()}` | Згенерувати UUID (36 символів). |
| `${__threadNum}` | Номер поточного потоку. |
| `${__counter(FALSE)}` | Лічильник, спільний для потоків у межах запуску; значення може повторитися після нового запуску. |
| `${__P(users,5)}` | Отримати JMeter property `users`, якщо відсутня — використати `5`. |

Якщо поле БД обмежене, потрібно перевіряти довжину згенерованих даних. Для полів із `UNIQUE` враховуйте повторні запуски та паралельні потоки.

**Assertions** відповідають за логічну правильність результату. Наприклад, HTTP `200` не гарантує, що поле `status` містить очікувану бізнес-ознаку. За потреби перевіряють і статус, і вміст відповіді. Не слід надсилати залежні GET/UPDATE після невдалого CREATE із відсутнім ID.

## 5. Метрики: що саме читати

| Показник | Як інтерпретувати |
|---|---|
| **Samples** | Кількість зафіксованих виконань Sampler. Не плутати з кількістю завершених бізнес-сценаріїв. |
| **Average** | Середня тривалість відповіді; окремі повільні запити можуть бути непомітними на середньому. |
| **Median (p50)** | 50% вимірювань не перевищують цього значення. |
| **p95 / 95% Line** | 95% вимірювань мають час відповіді не більший за цей показник. |
| **p99** | Характеризує повільну «хвостову» частину запитів. |
| **Min / Max** | Найшвидший і найповільніший зафіксовані запити. |
| **Error %** | Частка невдалих Samplers з урахуванням результатів та налаштованих перевірок. |
| **Throughput** | Швидкість обробки запитів, наприклад requests/s; уточнюйте одиницю у звіті. |
| **Active Threads Over Time** | Скільки JMeter-потоків були активними у часі. |

**Aggregate Report** дає зведення за кожним Sampler і підсумковий `TOTAL`. **Summary Report** дає компактну статистику. **View Results Tree** корисний для розбору окремих HTTP-запитів, але не для масштабного збору всіх відповідей.

Порівнювати варто не лише `TOTAL`, а й окремі операції: створення, читання, оновлення можуть мати різні затримки. Показники в одному загальному звіті за staged тест **агрегують усі фази**: загальний p95 не дорівнює p95 найнавантаженішої фази.

## 6. CLI / non-GUI: запуск і HTML-звіт

Приклад для **PowerShell у Windows** (шляхи умовні):

```powershell
& "C:\tools\apache-jmeter\bin\jmeter.bat" -n `
  -t ".\performance-test.jmx" `
  -l ".\results\run-01.jtl" `
  -e `
  -o ".\results\run-01-report"
```

> Символ `` ` `` наприкінці рядка — **PowerShell line continuation**, він дозволяє записати одну команду на кількох рядках. Після нього не повинно бути пробілів. Можна записати все одним рядком. Оператор `&` запускає шлях до виконуваного файла, взятий у лапки. Якщо `jmeter` уже доступний у `PATH`, достатньо команди `jmeter`.

### Розшифрування параметрів

| Частина команди | Значення |
|---|---|
| `jmeter.bat` | Windows-скрипт запуску JMeter. |
| `-n` | Non-GUI / CLI mode. |
| `-t performance-test.jmx` | Завантажити й виконати вказаний Test Plan. |
| `-l run-01.jtl` | Записати результати окремих Samplers у файл JTL. |
| `-e` | Після тесту згенерувати Dashboard. |
| `-o run-01-report` | Папка для HTML Dashboard; вона має бути відсутня або порожня. |

Файл результатів і директорії для них слід підготувати завчасно; не перезаписуйте випадково дані попередніх вимірювань. Для кожного запуску зручно використовувати окрему назву файлу та звіту.

**Генерація HTML Dashboard із уже отриманого JTL** без повторного тестування:

```powershell
& "C:\tools\apache-jmeter\bin\jmeter.bat" -g ".\results\run-01.jtl" -o ".\results\run-01-report"
```

Параметр `-g` читає наявний файл результатів, а `-o` задає каталог HTML-звіту. Необхідно, щоб JTL містив поля та формат, сумісні з генератором звітів.

**Корисні додаткові прапорці:**

```text
-j <path>         окремий лог роботи JMeter
-Jname=value     передати JMeter property зі значенням
-h               коротка довідка
-v               версія JMeter
```

Наприклад, властивості для параметризованого Test Plan можна передавати без редагування `.jmx`:

```powershell
jmeter -n -t ".\performance-test.jmx" -l ".\results\run-02.jtl" -e -o ".\results\run-02-report" -Jusers=20
```

Водночас `-Jusers=20` **нічого не змінить саме по собі**, якщо Thread Group або інший елемент Test Plan не використовує цю property, наприклад `${__P(users,5)}`.

На Linux/macOS зазвичай використовується виконуваний скрипт `bin/jmeter`, а перенесення рядків у shell записують через `\` замість PowerShell backtick.

## 7. HTML Dashboard і графіки

Після успішної генерації відкрийте `index.html` у папці звіту. Залежно від конфігурації JMeter Dashboard містить:

- **Statistics:** samples, average, p95, errors, throughput за кожною операцією;
- **Response Times Over Time / Response Time Percentiles Over Time:** як змінювалася швидкість відповіді;
- **Hits per Second / Transactions per Second:** інтенсивність запитів або транзакцій;
- **Active Threads Over Time:** фактична кількість активних потоків;
- **Response Codes / Errors:** помилки за типом і часом;
- **APDEX:** оцінка часу відповіді відносно окремо заданих порогів задовільності.

**APDEX не тотожний threshold `p95 < ...`** і не замінює його перевірку. Аналогічно, **Duration Assertion** контролює час *окремого виконання* Sampler, а не агрегований p95 тесту. Для лабораторної можна визначити критерії прийнятності до запуску та порівняти їх з фактичними метриками звіту.

### Деталізація графіків

За замовчуванням часова гранулярність JMeter Dashboard — **60 000 ms (1 хвилина)**. Для коротких тестів це може приховати форму стрибка навантаження. Наприклад, передати гранулярність 5 секунд можна так:

```powershell
jmeter -n -t ".\performance-test.jmx" -l ".\results\run-03.jtl" -e -o ".\results\run-03-report" -Jjmeter.reportgenerator.overall_granularity=5000
```

Не встановлюйте значення **1000 ms або нижче**: документація попереджає, що це може викривляти throughput-графіки. Параметр можна також визначити через `user.properties`. Графіки та усереднені значення різних звітів можуть дещо відрізнятися через методи агрегації та оцінювання процентилів.

## 8. Як коректно інтерпретувати навантаження

- **Не потрібно спеціально «ламати» SUT.** Якщо збільшення навантаження не викликало помилок — це також результат експерименту.
- **Фіксуйте середовище:** CPU, RAM, операційна система, розміщення JMeter/SUT/БД, версії інструментів.
- **Не плутайте обмеження генератора й сервера:** коли вони працюють на одному комп’ютері, вони конкурують за ресурси.
- **Контролюйте дані:** повторні записи, конфлікти `UNIQUE`, зростання БД та різний початковий стан можуть впливати на результати.
- **Переконайтеся, що запити успішні не лише технічно, а й бізнесово:** дивіться Assertions, а не лише статус сервера.
- **Для порівняння JMeter та іншого інструмента** використовуйте той самий SUT, послідовність операцій, профіль VUs/часу, тестові дані або еквівалентні умови, а також однакові критерії. Навіть тоді абсолютні цифри можуть відрізнятися.
- **Не порівнюйте різні фази лише за одним TOTAL:** бажано аналізувати графіки в часі та характеристики окремих операцій.

## 9. Що студент має вміти пояснити на захисті

Сценарій і джерело даних; різницю між VUs і requests/s; як працюють Ramp-up, Loop Count та Duration; як передаються значення між HTTP-запитами; що саме перевіряють Assertions; чому вимірювання проводили у CLI; звідки взялися JTL і Dashboard; що означають average, p95, throughput, error rate; як змінювалися графіки у зв’язку з профілем навантаження; які обмеження має експеримент.

Завдання студента — **обґрунтувати налаштування, показати відтворювані результати й пояснити поведінку системи**, а не отримати якомога більше requests/s.
