# Grafana k6 — довідник для лабораторної роботи з Performance and Load Testing

> **Призначення:** короткий технічний орієнтир щодо можливостей k6. Це **не покрокова інструкція з виконання лабораторної** і не готовий розв’язок для конкретного REST API. Сценарій, профілі навантаження, критерії та висновки студент проєктує самостійно.

## 1. Що таке k6

**Grafana k6** — інструмент для навантажувального тестування, у якому поведінку віртуальних користувачів описують JavaScript-кодом. k6 виконує HTTP-запити, збирає часові та кількісні метрики, перевіряє умови коректності і може формувати графічні звіти.

Основні поняття:

| Поняття | Значення |
|---|---|
| **SUT** (System Under Test) | Система, яку тестують |
| **VU** (virtual user) | Віртуальний користувач, який повторює сценарій |
| **Iteration** | Один повний виклик функції сценарію одним VU |
| **Workload** | Модель навантаження: кількість VUs/частота запусків, тривалість, паузи, профіль у часі |
| **Scenario** | Налаштований спосіб виконання сценарію (executor, VUs, stages тощо) |
| **Check** | Перевірка відповіді або бізнес-умови; сама по собі не зупиняє тест |
| **Threshold** | Критерій прийнятності для агрегованої метрики, наприклад p95 або частки помилок |

## 2. Із чого складається JavaScript-сценарій

Типові елементи файлу `*.js`:

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 2,
  duration: '15s',
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

const BASE_URL = __ENV.BASE_URL || 'http://127.0.0.1:8080';

export default function () {
  const response = http.get(`${BASE_URL}/health`, {
    tags: { name: 'GET /health' },
  });
  check(response, { 'HTTP 200': (r) => r.status === 200 });
  sleep(1);
}
```

**Цей фрагмент демонструє синтаксис, а не відповідає вимогам лабораторної:** він містить лише один незалежний HTTP-запит.

- `import` — підключення модулів k6.
- `options` — конфігурація запуску й критерії прийнятності.
- `__ENV` — передавання налаштувань через змінні середовища.
- `export default function()` — логіка однієї ітерації віртуального користувача.
- `http.get/post/put/delete(...)` — виконання HTTP-запитів.
- `check(response, {...})` — логічні перевірки.
- `sleep(seconds)` — пауза між діями; її наявність суттєво впливає на інтенсивність навантаження.

k6 використовує JavaScript, але **не є Node.js**: не всі Node API й npm-пакети доступні без додаткової підготовки.

## 3. Пов’язані HTTP-операції та тестові дані

У реальному API-сценарії наступний запит часто залежить від відповіді попереднього: наприклад, отриманий JSON `id` використовується в URL наступної операції. Для цього можна читати `response.json('id')` і зберігати результат у локальну змінну.

Важливо передбачити:

- коректні початкові дані й авторизацію, якщо вона потрібна;
- унікальні значення для полів із обмеженням `UNIQUE`;
- контроль очікуваних HTTP-статусів і бізнес-результату;
- поведінку сценарію після невдалої передумови (не надсилати наступні запити з невалідним ID);
- вплив створених даних на повторні запуски й однаковість умов порівняння.

`check()` **лише фіксує результат перевірки**. Для переривання невдалої ітерації потрібна явна логіка — наприклад, `return` або `fail()` із відповідним наслідком. Перевірки `checks` та мережеві/HTTP-помилки `http_req_failed` — не одна й та сама метрика.

### Групування однотипних URL

Якщо шлях містить випадковий або згенерований ID, корисно дати запиту стабільну назву:

```javascript
http.get(`${BASE_URL}/items/${itemId}`, {
  tags: { name: 'GET /items/{id}' },
});
```

Це дозволяє порівнювати одну логічну операцію замість створення безлічі окремих метрик за унікальними URL. Без такого групування можливий **high cardinality** — надмірна кількість часових рядів.

## 4. Налаштування навантаження

### Прості параметри

- `vus` — кількість одночасних VUs;
- `iterations` — загальна кількість ітерацій у відповідному простому режимі;
- `duration` — тривалість тесту;
- `stages` — послідовні фази зміни кількості VUs (`duration`, `target`).

Приклад **профілю, а не готової лабораторної**:

```javascript
export const options = {
  stages: [
    { duration: '10s', target: 5 },
    { duration: '20s', target: 15 },
    { duration: '10s', target: 0 },
  ],
};
```

`target` означає кількість VUs **на кінець фази**. Зміна кількості користувачів відбувається поступово протягом відповідної фази. Для складнішої моделі використовують `options.scenarios` та **executors** (наприклад, `constant-vus`, `ramping-vus`, `constant-arrival-rate`, `ramping-arrival-rate`).

**Важлива відмінність:** VUs — це конкуренція, а не гарантована кількість HTTP-запитів за секунду. У закритій моделі (VUs повторюють сценарій) швидкість запитів залежить від тривалості ітерацій та пауз. Для керування швидкістю *початку ітерацій* використовують arrival-rate executors.

### Типові види тестів

| Тип | Ідея |
|---|---|
| **Baseline** | Невелике стабільне навантаження як початкова точка порівняння |
| **Load** | Перевірка під очікуваним або поступово зростаючим навантаженням |
| **Stress** | Підвищене навантаження та спостереження за поведінкою системи |
| **Spike** | Короткий різкий стрибок і подальше зниження навантаження |

Для навчального експерименту **не потрібно навмисно спричиняти відмову або обов’язково знаходити bottleneck**. Значення навантаження добирають з урахуванням SUT та доступного обладнання.

## 5. Метрики та їх інтерпретація

| Метрика k6 | Значення |
|---|---|
| `http_reqs` | Кількість HTTP-запитів; у підсумку також відображається середня інтенсивність, req/s |
| `http_req_duration` | Тривалість оброблення HTTP-запиту (без початкового встановлення з’єднання), із `avg`, `med`, `p(90)`, `p(95)` тощо |
| `http_req_failed` | Частка HTTP-запитів, які k6 вважає невдалими за своїм критерієм expected response |
| `checks` | Частка успішних логічних перевірок |
| `iteration_duration` | Час повної ітерації сценарію, включаючи паузи |
| `vus` / `vus_max` | Активні / доступні віртуальні користувачі |
| `http_req_waiting` | Час очікування першого байта відповіді (TTFB) |

**p95** означає, що 95% вимірювань цієї метрики не перевищили вказаного часу. `http_req_duration p95` — не те саме, що `iteration_duration p95`.

**Throughput** треба називати з одиницями виміру: **HTTP requests/second** або **повних сценаріїв/second**. Три HTTP-запити в одній ітерації — це не три незалежні бізнес-сценарії.

Загальний p95 за багатофазний тест об’єднує різні рівні навантаження. Щоб пояснювати поведінку саме під час spike або відновлення, потрібні часові графіки/фільтрація за періодом.

## 6. Checks і thresholds

Приклади:

```javascript
check(response, {
  'status is 200': (r) => r.status === 200,
});

export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500'], // 95-й перцентиль < 500 мс
    http_req_failed: ['rate<0.01'],   // менше 1% помилкових HTTP-запитів
    checks: ['rate>0.99'],           // більше 99% успішних перевірок
  },
};
```

Цифри — **навчальні приклади**, а не універсальні стандарти. Критерії варто визначати **до** проведення експерименту та обґрунтувати. Якщо threshold не виконаний, k6 позначає запуск як неуспішний (це не обов’язково означає, що весь SUT «зламався»). Звичайний `check()` без threshold сам по собі не гарантує неуспішний статус процесу.

Пороги можна застосовувати й до окремих операцій через теги, наприклад:

```javascript
'http_req_duration{name:GET /items/{id}}': ['p(95)<300']
```

## 7. Команди командного рядка

Основні приклади для **PowerShell**:

```powershell
k6 version
k6 run .\k6\test.js
k6 run --vus 5 --duration 30s .\k6\test.js
k6 run --summary-export results-summary.json .\k6\test.js
k6 run --out json=results-raw.json .\k6\test.js
```

| Частина команди | Для чого |
|---|---|
| `k6 run` | Запуск тестового сценарію |
| `--vus 5` | П’ять VUs (для відповідних простих конфігурацій; не замінює складні `scenarios`) |
| `--duration 30s` | Тривалість запуску |
| `--summary-export ...` | Запис підсумкової агрегованої статистики в JSON |
| `--out json=...` | Потік вимірювань із часовими позначками в JSON (файл може бути великим) |
| `-e NAME=value` | Передача значення у `__ENV.NAME` всередині сценарію |

Приклад параметризації сервера:

```powershell
k6 run -e BASE_URL=http://127.0.0.1:8080 .\k6\test.js
```

Не слід плутати `-e BASE_URL=...` (змінна, доступна у сценарії) та системні `K6_*` змінні налаштування самого k6.

## 8. Web Dashboard та HTML Report

k6 має **вбудований Web Dashboard**: його не потрібно встановлювати як окрему Grafana-систему. Він дозволяє переглядати графіки VUs, кількості запитів, затримок і помилок протягом запуску.

Приклад для **PowerShell**:

```powershell
$env:K6_WEB_DASHBOARD = 'true'
$env:K6_WEB_DASHBOARD_OPEN = 'true'
$env:K6_WEB_DASHBOARD_PERIOD = '2s'
$env:K6_WEB_DASHBOARD_EXPORT = 'k6-report.html'

k6 run .\k6\test.js
```

| Налаштування | Пояснення |
|---|---|
| `K6_WEB_DASHBOARD=true` | Активує локальну вебпанель |
| `K6_WEB_DASHBOARD_OPEN=true` | Відкриває панель у браузері |
| `K6_WEB_DASHBOARD_PERIOD=2s` | Інтервал агрегації/оновлення даних для панелі; впливає на деталізацію |
| `K6_WEB_DASHBOARD_EXPORT=k6-report.html` | Після завершення зберігає самодостатній HTML-звіт |

За замовчуванням вебпанель доступна за адресою **http://127.0.0.1:5665**. HTML-звіт можна відкрити окремо, без запущеного k6. Для коротких тестів обирайте інтервал агрегації, який дозволяє побачити кілька точок на графіку.

**Важлива особливість:** після завершення навантаження процес k6 може **не виходити, поки відкрита вкладка браузера з live dashboard**. Закрийте її, якщо тест завершений і звіт збережений. Це документована поведінка, а не обов’язково зависання. Для автоматизованого середовища можна вимкнути порт dashboard через `K6_WEB_DASHBOARD_PORT=-1`, залишивши експорт HTML.

Відповідно до документації, HTML-графіки формуються, якщо тривалість тесту перевищує три інтервали агрегації.

## 9. Як читати графіки

Для лабораторної важливо не тільки надати звіт, а й **пояснити причинно-часові зв’язки**:

- **Active VUs / concurrency over time** — чи було створено запланований профіль навантаження.
- **Request rate / throughput over time** — як змінювалася фактична кількість запитів за секунду.
- **Response time (включно з p95) over time** — чи зростала затримка під навантаженням і чи зменшувалася після нього.
- **Error rate / checks** — чи залишався сценарій коректним; нуль помилок теж слід показати.

Саме по собі зростання p95 під час spike **не доводить конкретний bottleneck**. Порівняння графіків допомагає описати спостереження, але для діагнозу причини зазвичай потрібні додаткові серверні метрики.

## 10. Надійність результатів і типові помилки

- Не порівнюйте абсолютні req/s між різними комп’ютерами як оцінку якості роботи студента.
- Не змішуйте запуск із `sleep()` та без нього, якщо хочете порівняти однакові профілі.
- Не називайте єдиний `p95` за всі фази точним p95 конкретного рівня навантаження.
- Уникайте високої кардинальності тегів: не підставляйте у `name` унікальні IDs або UUID.
- Уникайте повторного використання унікальних бізнес-ключів між запусками.
- Звертайте увагу на початковий стан БД і накопичення записів.
- Якщо генератор і SUT працюють на одному ПК, їхня конкуренція за CPU/RAM впливає на результати.
- Фіксуйте версію k6, тестове середовище, сценарій, параметри й команду запуску.
- Під час порівняння k6 та JMeter узгоджуйте кількість користувачів, профілі навантаження, запити, паузи та критерії перевірок; навіть тоді результати можуть відрізнятися.

## 11. Що варто вміти пояснити на захисті

Студент має розуміти призначення основних конструкцій власного сценарію, як змінювалося навантаження, звідки беруться метрики й графіки, за якими критеріями оцінювався результат, а також які обмеження має виконаний експеримент. **Демонстрація самого HTML Dashboard без пояснення недостатня.**
