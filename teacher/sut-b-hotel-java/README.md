# SUT B — Бронювання готелю

Пілот для лабораторної №4 «Інтеграційне тестування та тестування бази даних». Java 21, Maven, PostgreSQL 17, JDBC та JUnit 5. Навмисних дефектів у цьому SUT немає. Це окрема спрощена система: правила попереднього SUT A автоматично на неї не переносяться.

## Межа тестування

`BookingService → JdbcRoomRepository / JdbcBookingRepository → PostgreSQL`

Репозиторії та БД у інтеграційних тестах реальні. `BookingPolicy` — зовнішня перевірка дозволу; студент передає власний Stub/Mock. Для локальних прикладів достатньо Stub/Mock. Окремий контейнерний профіль використовує реальний HTTP-адаптер і WireMock.

## Модель

- `Room`: ідентифікатор, унікальний номер, місткість 1–4, ціна ночі 100–10 000 000 копійок.
- `Booking`: ідентифікатор, унікальний код, посилання на номер, 1–30 ночей, 1–4 гостей, сума, статус.
- `BookingStatus`: `CONFIRMED` або `CANCELLED`. Цим значенням відповідає довідник `booking_status` у БД.

Один номер має багато бронювань. Видалити номер із бронюваннями не можна: спочатку треба видалити залежні записи. Скасування бронювання не видаляє його.

## Правила сервісу

`createBooking(BookingRequest request)`:

1. Код обов’язковий, не порожній і не складається лише з пробілів; довжина до 40 символів. Ідентифікатор номера додатний. Ночі — 1–30, гості — 1–4 включно.
2. Номер має існувати; гостей не може бути більше за його місткість.
3. Після цих перевірок один раз викликається `BookingPolicy.isAllowed(room, nights, guests)`. Відмова або виняток зупиняє операцію без створення бронювання.
4. Базова сума — ціна ночі × кількість ночей. Від 7 ночей надається знижка 5%; сума знижки округлюється донизу до копійки.
5. Створюється одне бронювання зі статусом `CONFIRMED`; повертається збережений об’єкт із призначеним БД ідентифікатором.

`cancelBooking(id)`:

1. Ідентифікатор додатний, бронювання має існувати.
2. Повторне скасування відхиляється.
3. Статус змінюється на `CANCELLED`, решта даних зберігається. Зовнішня перевірка не викликається.

Некоректний вхід або відсутній запис: `IllegalArgumentException`. Відмова політики або перевищення місткості: `BookingRejectedException`; повторне скасування: `IllegalStateException`. Помилки репозиторіїв, включно з порушенням обмежень БД: підтипи `DataAccessException`; виняток зовнішньої залежності передається виклику без приховування.

Календар, зайнятість на конкретні дати, оплата та конкурентні запити не входять у модель. Кілька бронювань одного номера дозволені. Багатокрокових змін БД та окремого завдання на rollback немає; кожна операція сервісу виконує один запис у БД. У звичайному режимі JDBC він зберігається через auto-commit.

## Репозиторії та обмеження БД

`RoomRepository`: `create`, `findById`, `update`, `delete`.

`BookingRepository`: `create(Booking) → long`, `findById(id) → Booking`, `updateStatus`, `delete`, `findBookings(roomId, status)`, `findAll()`.

Пошук відсутнього бронювання повертає `null`; пошук відсутнього номера — `Optional.empty()`. `create(Booking)` повертає новий ідентифікатор, вхідний `id` ігнорується; статус береться з переданого об’єкта. `findAll()` повертає всі бронювання поточної схеми за зростанням id. Видалення відсутнього запису нічого не змінює; оновлення відсутнього запису спричиняє `IllegalArgumentException`. Фільтр враховує одночасно номер і статус, повертає записи за зростанням ідентифікатора; за відсутності збігів — порожній список.

БД має `PRIMARY KEY`, `UNIQUE` для номера кімнати й коду бронювання, `NOT NULL`, зовнішні ключі та `CHECK` для числових діапазонів. Репозиторії не підміняють перевірки БД валідацією сервісу: constraints можна перевіряти прямими викликами репозиторію. Обмеження місткості конкретного номера та розрахунок ціни перевіряє сервіс.

## Локальна підготовка

Потрібні JDK 21+, Maven та встановлений PostgreSQL 17. Команди виконуються з цієї папки. `psql` має бути в PATH; у Windows він зазвичай розташований у `C:\Program Files\PostgreSQL\17\bin`.

Увійдіть адміністратором локальної БД:

```sh
psql -U postgres -d postgres
```

Створіть окремого навчального користувача та порожню тестову БД:

```sql
CREATE ROLE hotel_lab LOGIN;
\password hotel_lab
CREATE DATABASE hotel_lab_test OWNER hotel_lab;
\q
```

Пароль задайте власний. Потім послідовно застосуйте міграції:

```sh
psql -h localhost -U hotel_lab -d hotel_lab_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U hotel_lab -d hotel_lab_test -v ON_ERROR_STOP=1 -f migrations/V2__seed_statuses.sql
```

Це два звичайні SQL-файли для одноразового застосування до нової БД, без окремого фреймворку міграцій. Повторно перед кожним тестом їх виконувати не треба. Міграції створюють лише схему й два статуси; номери та бронювання створюють самі тести.

Тестова конфігурація: `src/main/resources/database-test.properties`. Значення можна перевизначити змінними середовища `DB_URL`, `DB_USER`, `DB_PASSWORD`. Пароль у репозиторій не записується.

Приклад для PowerShell:

```powershell
$env:DB_URL = 'jdbc:postgresql://localhost:5432/hotel_lab_test'
$env:DB_USER = 'hotel_lab'
$secret = Read-Host 'Пароль тестової БД' -AsSecureString
$env:DB_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
mvn test
```

Для перевірки компіляції без запущеної БД: `mvn -DskipTests package`.

## Як створити компоненти в тесті

Відкрийте з’єднання через `Database.fromEnvironment().connect()`. Передайте його конструкторам `JdbcRoomRepository` та `JdbcBookingRepository`, а обидва репозиторії й тестовий `BookingPolicy` — у `BookingService`. З’єднання закриває той, хто його відкрив; репозиторії його не закривають.

Допоміжний `EnvironmentTest` перевіряє тільки доступність БД; демонстраційні сценарії містить `BookingIntegrationTest`. Це перевірка налаштування, а не розв’язок лабораторної; до мінімуму змістовних тестів її не зараховуйте. Окремий сервер застосунку запускати не потрібно: сервіс викликається безпосередньо з тестів.

## Завдання студенту

Напишіть щонайменше 10 змістовних інтеграційних тестів, які разом перевіряють:

- CRUD і пошук відсутнього запису;
- фільтрацію за номером та статусом, включно з відсутністю збігів;
- зв’язок між номером і бронюваннями;
- щонайменше два обмеження саме БД;
- успішну операцію сервісу та негативний сценарій;
- вплив зовнішньої залежності через Stub/Mock;
- фактичні збережені значення після операції.

Перевіряйте результат повторним читанням із БД, а не лише поверненим об’єктом. Успішно збережені дані можна читати через нове з’єднання. Для негативного сценарію перевіряйте також відсутність небажаних записів.

Кожен тест створює свої дані й очищає їх у завершенні, навіть після невдалої перевірки. Спочатку видаляйте створені бронювання, потім номери. Довідник статусів не очищайте. Використовуйте унікальні коди та номери в межах дозволеної довжини; не прив’язуйтеся до конкретних згенерованих id. Повторний запуск набору не повинен вимагати ручного очищення БД.

## Обсяг пілота

Це зразок структури для погодження, а не розгортання всіх варіантів. Для наступної роботи можна передати адресу тимчасової PostgreSQL через ту саму конфігурацію й застосувати ті самі міграції. Контейнерні демонстрації описані нижче.

## Демонстрація за лекцією 4

`BookingIntegrationTest` — один викладацький клас із 10 тестами: 2 перевірки репозиторію, 3 перевірки query та 5 сервісних сценаріїв. Використовується Mockito; репозиторії та PostgreSQL залишаються реальними. `BookingRequest` містить reference, roomId, nights, guests.

Кожен тест створює власну схему `lecture_<випадковий код>` у налаштованій тестовій БД, застосовує до неї готові міграції та видаляє тільки цю схему після завершення. Користувач БД повинен мати право CREATE на тестову БД; її власник має це право. Тому перевірка `findAll().isEmpty()` не залежить від даних інших тестів. ROLLBACK у завершенні — лише технічне очищення після можливої помилки міграції, не навчальна перевірка бізнес-транзакції.

Запуск лише демонстрацій: `mvn -Dtest=BookingIntegrationTest test`. Повторіть команду, щоб перевірити незалежність запусків. Метод query вже реалізовано; під час лекції його код можна розбирати поряд із тестами.

## PostgreSQL і WireMock через Testcontainers

Запустіть Docker із підтримкою Linux-контейнерів, потім із папки проєкту:

```sh
mvn -Pcontainers test
```

Профіль запускає лише BookingContainersIT: два контейнери на тестовий клас, автоматичні міграції V1 та V2, чотири сценарії. Параметри PostgreSQL та адреса WireMock отримуються під час запуску контейнерів. Локальна PostgreSQL і конфігураційний файл для цього профілю не потрібні. Стандартний mvn test зберігає попередні локальні тести.

Перед кожним тестом очищаються бронювання й номери, скидаються налаштування та журнал WireMock. Тести виконуються послідовно. JUnit/Testcontainers керує зупинкою контейнерів після класу; повторний запуск створює нові контейнери без повторного використання даних. Спільна Docker-мережа не потрібна: Java-процес звертається до обох контейнерів через опубліковані порти.

HttpBookingPolicy реалізує BookingPolicy. POST /booking-policy передає JSON із roomId, nights та guests. Коректна відповідь: HTTP 200 і JSON із логічним allowed. False означає бізнес-відмову; інший статус, некоректний JSON або мережевий збій — IllegalStateException без запису бронювання. Таймаут задається конструктору, повторних запитів немає. Сервіс і його бізнес-правила не змінені.

Сценарії перевіряють незалежним SQL-запитом стан PostgreSQL, а через журнал WireMock — кількість і тіло HTTP-запитів: успіх зі знижкою, зовнішня відмова, HTTP 503 та локальна відмова без HTTP. Щоб підтвердити незалежність від локальної БД, зупиніть її та двічі виконайте команду вище після завершення попереднього запуску.

## Альтернативна демонстрація за лекцією 5

Попередній `BookingContainersIT` залишається без змін: SQL-міграції через JDBC та налаштування WireMock через HTTP Admin API.

`BookingContainersSlidesIT` перевіряє ті самі чотири сценарії, але використовує Flyway для міграцій та Java DSL WireMock (`stubFor`, `verify`, `matchingJsonPath`). Допоміжні `BookingRow` і `readBooking` читають фактичний стан БД через окреме з’єднання. Бізнес-код спільний для обох демонстрацій.

```sh
mvn -Pcontainers test
mvn -Pcontainers-slides test
```

Кожна команда запускає лише відповідну демонстрацію. Потрібен Docker; локальна PostgreSQL не потрібна. Обидва варіанти створюють власні контейнери, очищають дані та журнал HTTP перед кожним тестом і зупиняють контейнери після завершення класу.

Maven копіює наявні SQL-файли з `migrations` у тестовий classpath `db/migration`; окремих копій вихідних міграцій немає. Flyway застосовує їх один раз перед тестами й веде таблицю історії. Оскільки SQL-файли вже керують транзакціями через `BEGIN` та `COMMIT`, у цьому прикладі вимкнено додаткове обгортання міграцій транзакцією Flyway.

## REST API

Після налаштування PostgreSQL і застосування наявних міграцій запустіть із папки проєкту:

```sh
mvn spring-boot:run
```

Адреса за замовчуванням — `http://127.0.0.1:8080`; порт задається через `API_PORT`. Підключення до БД використовує наявні `DB_URL`, `DB_USER`, `DB_PASSWORD`. Міграції при запуску API автоматично не виконуються. Зупинка — Ctrl+C.

Без `BOOKING_POLICY_URL` зовнішня політика дозволяє бронювання; локальні бізнес-перевірки діють. Якщо задати цю змінну базовою адресою WireMock, використовується HttpBookingPolicy. Авторизації немає.

| Метод і шлях | Результат |
|---|---|
| `POST /rooms` | Створення номера, `201` |
| `GET /rooms/{id}` | Читання номера, `200` або `404` |
| `POST /bookings` | Створення бронювання, `201` |
| `GET /bookings/{id}` | Читання бронювання, `200` або `404` |
| `POST /bookings/{id}/cancel` | Скасування, `200`; повторне — `409`; невідомий id — `404` |

Тіло створення номера:

```json
{"number":"API-101","capacity":2,"nightlyPrice":120000}
```

Візьміть `id` із відповіді та передайте як `roomId`:

```json
{"reference":"API-B1","roomId":1,"nights":7,"guests":2}
```

Відповідь бронювання містить `id`, `reference`, `roomId`, `nights`, `guests`, `total`, `status`. Для прикладу total=798000, status=`CONFIRMED`. Створення повертає заголовок `Location`. Скасування не потребує тіла, повертає бронювання зі статусом `CANCELLED`; сума не змінюється.

Помилки мають поля `code` та `message`. Неіснуючий ресурс — `404`; бізнес-відмова, повторне скасування чи дубль коду — `409`. Некоректний запит — `400`, непідтримуваний метод — `405`, збій зовнішньої політики — `502`, внутрішня помилка БД — `500`.

API не видаляє дані після зупинки. Для незалежних сценаріїв використовуйте власну тестову БД та унікальні коди; очищення організовує тестове оточення. Spring Boot налаштовує DataSource із пулом HikariCP; JdbcTemplate бере з’єднання на час SQL-операції та повертає його в пул. Для навчальних сценаріїв використовуйте послідовні запити: захист конкурентних бізнес-операцій не входить до моделі.

`BookingControllerTest` запускає Spring Boot на випадковому порту й перевіряє HTTP-маршрути з реальним сервісом і підміненими репозиторіями; це не перевірка PostgreSQL. Запуск: `mvn -Dtest=BookingControllerTest test`.

API реалізовано через Spring Boot: `BookingController` і `RoomController` — REST-контролери, `ApiExceptionHandler` — спільна обробка помилок. В IDE запускайте `BookingApi.main()`. `BookingService` позначено `@Service`, JDBC-репозиторії — `@Repository`; залежності передаються через конструктори. `ApiConfiguration` лише вибирає локальну або HTTP-політику. Міграції та попередні локальні й контейнерні тести залишаються окремими.

### Доступ до БД через Spring

Репозиторії використовують `JdbcTemplate`, а параметри `spring.datasource.*` визначено в `application.properties`. Змінні `DB_URL`, `DB_USER`, `DB_PASSWORD` перевизначають значення з наявного `database-test.properties`. SQL і бізнес-правила збережені; ORM не використовується.

Конструктори репозиторіїв із `Connection` залишені для попередніх інтеграційних тестів. Вони використовують `SingleConnectionDataSource` без закриття переданого з’єднання: ним далі керує сам тест. У Spring-застосунку автоматично використовується конструктор із `JdbcTemplate`.

### Автоматизовані API-тести

`BookingApiIT` використовує RestAssured, Spring Boot і PostgreSQL у Testcontainers: 10 запусків сценаріїв без підміни репозиторіїв. Запуск із Docker: `mvn -Dtest=BookingApiIT test`. Контейнерна БД і міграції готуються автоматично; звичайний `mvn test` цей клас не запускає.

Покрокова інструкція з прикладами запитів, скриптів Postman і запуском Newman: [API-TESTING.md](API-TESTING.md).
