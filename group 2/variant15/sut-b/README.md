# SUT B — Доставка посилок, варіант 15

JavaScript, Node.js 22+, PostgreSQL 17, pg та Jest.

## Спільні правила

Клієнт має унікальний непорожній code до 40 символів та ознаку regular. Посилка має окремий унікальний code до 40 символів, вагу 1–30 000 грамів, оголошену вартість 0–100 000 000 копійок і три сторони по 1–200 см. Сторони — цілі числа; конструктор Parcel за замовчуванням використовує 10 см для кожної пропущеної сторони. Відстань — ціле число 1–5000 км. Ідентифікатори заявок — додатні безпечні цілі JavaScript. Логічні ознаки — лише boolean.

Одна заявка містить одну посилку для одного клієнта. reference унікальний, непорожній, до 40 символів. Базовий тариф: 50 грн + 10 грн за кожен розпочатий кілограм + 0,10 грн за кілометр. При 1000 г і 100 км — 70 грн; при 1001 г і 100 км — 80 грн. Межі базового тарифу — 6010–85000 копійок.

createShipment перевіряє заявку, існування клієнта й посилки, параметри та персональні обмеження. Потім один раз викликає policy.isAllowed(customer, parcel, distanceKm). False — ShipmentRejectedError, відповідь іншого типу — TypeError; виняток залежності передається виклику. При відмовах запису немає.

Успіх створює Registered зі знімком ваги, сторін, оголошеної вартості, regular та сум. Подальші зміни карток не змінюють відправлення. baseFee — тариф, adjustment — доплата або від’ємна знижка, total = baseFee + adjustment. Початковий refund — 0.

Дозволені переходи: Registered → Dispatched → Delivered та Registered → Cancelled. Повторні переходи, доставка до відправлення й скасування після відправлення заборонені. При переходах зовнішній дозвіл не викликається. Скасування записує refund за збереженим total; інші суми залишаються незмінними. Крім варіанта з персональним збором при скасуванні, повертається весь total. У навчальній моделі total вважається сплаченим; реальних платежів немає.

pickup означає отримання у пункті видачі в місці призначення. Кілька відправлень можуть посилатися на одну картку посилки, але мають різні reference. Календар, маршрути й одночасна обробка не моделюються.

## Персональне правило — дозвіл за вагою та габаритами

Для оформлення вага має бути до 20 000 г, а кожна сторона — до 100 см одночасно. Відмова відбувається до зовнішньої перевірки й без запису. Картки посилок із більшими значеннями в межах загального діапазону зберігати дозволено.

Усі пороги включні, крім явно зазначеного «понад». Гроші — цілі копійки; відсоткова сума округлюється донизу один раз, потім застосовуються мінімум або максимум. Решта ознак, не згаданих у правилі, на розрахунок не впливає. Інших знижок чи доплат немає.

## API

`ShippingService(customers, parcels, shipments, policy)`:

- `calculateBaseFee(weightGrams, distanceKm)` — тариф;
- `isParcelAllowed(weightGrams, lengthCm, widthCm, heightCm)` — персональна функція;
- `calculateRefund(total)` — сума повернення при скасуванні; total — ціле число 0–135000 копійок;
- `createShipment(new ShipmentRequest(reference, customerId, parcelId, distanceKm, urgent=false, pickup=false))` — оформлення;
- `dispatch(id)`, `deliver(id)`, `cancel(id)` — зміни статусів.

Моделі експортуються з src/models.js. Customer(id, code, regular), Parcel(id, code, weightGrams, declaredValue, lengthCm=10, widthCm=10, heightCm=10), Shipment приймає об’єкт із полями збереженого відправлення.

Некоректні входи — TypeError/RangeError; відсутні записи — RangeError; бізнес-відмови — ShipmentRejectedError. Помилки БД передаються виклику.

CustomerRepository і ParcelRepository: create(model), findById(id), update(model), delete(id). ShipmentRepository: create(shipment), findById(id), findShipments(customerId, status), updateStatus(id, expected, next, refund), delete(id). Залежності можна замінити об’єктами з такими самими методами; policy — об’єкт з асинхронним isAllowed.

create повертає модель з id БД, ігноруючи вхідний id. findById повертає null за відсутності запису. findShipments застосовує обидва фільтри одночасно та сортує за id. update відсутнього клієнта/посилки — RangeError. updateStatus перевіряє допустимість переходу та поточний статус: заборонена пара — RangeError, відсутність відповідного запису — ShipmentRejectedError. Видалення відсутнього запису нічого не змінює. Клієнта чи посилку з відправленнями видалити не можна.

Усі методи з БД асинхронні: використовуйте await. Репозиторії отримують відкритий pg.Client; власник закриває його через await client.end(). Оформлення записує один рядок одним атомарним INSERT. Не використовуйте з’єднання паралельно. Реальної реалізації зовнішнього дозволу немає — передайте Stub/Mock.

## Підготовка та запуск

Із папки sut-b:

```sh
npm install
```

У локальній PostgreSQL створіть користувача (один раз) та окрему БД:

```sql
CREATE ROLE delivery_student LOGIN;
\password delivery_student
CREATE DATABASE delivery_variant15_test OWNER delivery_student;
```

Застосуйте міграцію один раз до порожньої БД:

```sh
psql -h localhost -U delivery_student -d delivery_variant15_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
```

Задайте змінні середовища за .env.example; файл .env автоматично не читається. Пароль — DB_PASSWORD.

```sh
npm test
```

Є лише тест підключення. Дані для сценаріїв готуйте у власних тестах. Схеми та дані автоматично не створюються й не очищаються. Для незалежності тестів видаляйте власні відправлення перед клієнтами й посилками або використовуйте окрему тестову схему.
