# SUT B — Доставка посилок, варіант 16

C#, .NET 8 SDK, PostgreSQL 17, Npgsql, xUnit та Moq.

## Спільні правила

Клієнт має унікальний непорожній код до 40 символів та ознаку Regular. Посилка має окремий унікальний непорожній код до 40 символів, вагу 1–30 000 грамів та оголошену вартість 0–100 000 000 копійок. Відстань доставки — ціле число 1–5000 км. Відправлення містить одну посилку для одного клієнта; його унікальний непорожній reference — до 40 символів. Ідентифікатори заявки додатні.

Базовий тариф: 50 грн + 10 грн за кожен розпочатий кілограм + 0,10 грн за кілометр. Наприклад, 1000 г і 100 км — 70 грн; 1001 г і 100 км — 80 грн. Гроші в API — цілі копійки; базовий тариф у межах 6010–85000 копійок.

CreateShipment перевіряє заявку, існування клієнта й посилки та допустимість параметрів. Потім один раз викликає IShippingPolicy.IsAllowed(customer, parcel, distanceKm). False означає ShipmentRejectedException; виняток залежності передається виклику. При цих відмовах відправлення не створюється.

Успіх створює Registered зі знімком ваги, оголошеної вартості, статусу клієнта та розрахованих сум. Подальші зміни клієнта чи посилки не змінюють збереженого відправлення. BaseFee — базовий тариф, Adjustment — доплата або від’ємна знижка, Total = BaseFee + Adjustment.

Дозволені переходи: Registered → Dispatched → Delivered та Registered → Cancelled. Повторні переходи, доставка до відправлення та скасування після відправлення заборонені. Перехід змінює лише статус; суми залишаються незмінними. Зовнішня залежність при зміні статусу не викликається.

Pickup означає отримання у пункті видачі в місці призначення; відстань і терміновість при цьому залишаються допустимими. Реальні платежі, маршрути, календар та одночасна обробка не моделюються. Кілька відправлень можуть посилатися на одну картку посилки; reference у них різні.

## Персональне правило — знижка за самовивіз і статус клієнта

10% базового тарифу за самовивіз та 5% постійному клієнту. Відсотки додаються: 0%, 5%, 10% або 15%. Знижка не може перевищувати 100 грн.

Усі зазначені пороги включні. Відсоткова сума округлюється донизу до цілої копійки один раз, потім застосовується мінімум або максимум. Решта ознак, не згаданих у правилі, не впливає на ціну. Інших доплат чи знижок немає.

## API

`ShippingService(customers, parcels, shipments, policy)`:

- `CalculateBaseFee(weightGrams, distanceKm)` — базовий тариф;
- `CalculateDiscount(baseFee, pickup, regular)` — персональний розрахунок, повертає невід’ємну суму в копійках;
- `CreateShipment(new ShipmentRequest(reference, customerId, parcelId, distanceKm, urgent=false, pickup=false))` — оформлення;
- `Dispatch(id)`, `Deliver(id)`, `Cancel(id)` — зміна статусу.

Некоректні входи й відсутні записи — ArgumentException або його підтипи; бізнес-відмови — ShipmentRejectedException. Помилки БД передаються виклику.

CustomerRepository та ParcelRepository: Create(model), FindById(id), Update(model), Delete(id). ShipmentRepository: Create(shipment), FindById(id), FindShipments(customerId, status), UpdateStatus(id, expected, next), Delete(id). Усі мають інтерфейси для Stub, Mock, Spy та Fake.

Create ігнорує вхідний id та повертає модель з id БД. FindById повертає null за відсутності запису. FindShipments застосовує обидва фільтри одночасно та сортує за id. Update відсутнього клієнта/посилки — ArgumentException. UpdateStatus перевіряє допустимість переходу та поточний статус; при відсутності відповідного запису — ShipmentRejectedException. Delete відсутнього запису нічого не змінює. Клієнта або посилку з відправленнями видалити не можна; спочатку видаляються відповідні відправлення.

Репозиторії отримують відкрите ADO.NET з’єднання. Власник закриває його через using. Операції виконуються синхронно; спільне з’єднання не використовується паралельно. Оформлення записує один рядок одним атомарним INSERT. Для IShippingPolicy передайте тестовий двійник; для HTTP-перевірки доступна реалізація HttpShippingPolicy.

## Підготовка та запуск

У локальній PostgreSQL створіть навчального користувача (один раз) та окрему БД:

```sql
CREATE ROLE delivery_student LOGIN;
\password delivery_student
CREATE DATABASE delivery_variant16_test OWNER delivery_student;
```

Із папки sut-b застосуйте міграцію один раз до порожньої БД:

```sh
psql -h localhost -U delivery_student -d delivery_variant16_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
```

Налаштуйте змінні середовища за .env.example; файл .env автоматично не читається. Пароль задається через DB_PASSWORD.

```sh
dotnet build Delivery.csproj
dotnet test tests/Delivery.Tests.csproj
```

Є лише тест підключення. Дані для сценаріїв готуйте у власних тестах. Схеми та дані автоматично не створюються й не очищаються при запуску тестів. Для незалежності тестів видаляйте власні відправлення перед клієнтами й посилками або використовуйте окрему тестову схему.

## HTTP-політика доставки

`HttpShippingPolicy` виконує зовнішню перевірку через HTTP. Додаткові пакети не потрібні.

```csharp
using var policy = new HttpShippingPolicy(new Uri(wiremockUrl), TimeSpan.FromSeconds(2));
var service = new ShippingService(customers, parcels, shipments, policy);
```

Адреса WireMock задається під час створення політики: базова HTTP(S)-адреса без шляху, з фактичним портом контейнера. Таймаут має бути додатним і скінченним. Власник звільняє політику через `using` після завершення викликів сервісу.

Після локальних перевірок сервіс надсилає один `POST /shipping-policy` з `Content-Type: application/json`:

```json
{"customerId":1,"parcelId":2,"distanceKm":100}
```

HTTP 200 із `{"allowed":true}` дозволяє зберегти відправлення зі статусом `Registered` і розрахованими сумами. HTTP 200 із `{"allowed":false}` спричиняє `ShipmentRejectedException` без нового запису. Інший HTTP-статус, некоректний JSON, відсутнє або нелогічне поле `allowed`, мережева помилка чи таймаут спричиняють `ShippingPolicyException`; відправлення також не створюється. Перенаправлення вимкнені; адаптер не реалізує повторних спроб.

Локальна відмова до перевірки політики не надсилає HTTP-запит. Зміна статусу відправлення також не звертається до HTTP-політики. Персональні правила залишаються чинними. У тестах перевіряйте фактичні записи PostgreSQL та кількість і тіло запитів у журналі WireMock.
