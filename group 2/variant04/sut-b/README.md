# SUT B — Доставка посилок, варіант 04

JavaScript, Node.js 22+, PostgreSQL 17, pg та Jest.

## Спільні правила

Клієнт має унікальний непорожній code до 40 символів та ознаку regular. Посилка має окремий унікальний code до 40 символів, вагу 1–30 000 грамів, оголошену вартість 0–100 000 000 копійок і три сторони по 1–200 см. Сторони — цілі числа; конструктор Parcel за замовчуванням використовує 10 см для кожної пропущеної сторони. Відстань — ціле число 1–5000 км. Ідентифікатори заявок — додатні безпечні цілі JavaScript. Логічні ознаки — лише boolean.

Одна заявка містить одну посилку для одного клієнта. reference унікальний, непорожній, до 40 символів. Базовий тариф: 50 грн + 10 грн за кожен розпочатий кілограм + 0,10 грн за кілометр. При 1000 г і 100 км — 70 грн; при 1001 г і 100 км — 80 грн. Межі базового тарифу — 6010–85000 копійок.

createShipment перевіряє заявку, існування клієнта й посилки, параметри та персональні обмеження. Потім один раз викликає policy.isAllowed(customer, parcel, distanceKm). False — ShipmentRejectedError, відповідь іншого типу — TypeError; виняток залежності передається виклику. При відмовах запису немає.

Успіх створює Registered зі знімком ваги, сторін, оголошеної вартості, regular та сум. Подальші зміни карток не змінюють відправлення. baseFee — тариф, adjustment — доплата або від’ємна знижка, total = baseFee + adjustment. Початковий refund — 0.

Дозволені переходи: Registered → Dispatched → Delivered та Registered → Cancelled. Повторні переходи, доставка до відправлення й скасування після відправлення заборонені. При переходах зовнішній дозвіл не викликається. Скасування записує refund за збереженим total; інші суми залишаються незмінними. Крім варіанта з персональним збором при скасуванні, повертається весь total. У навчальній моделі total вважається сплаченим; реальних платежів немає.

pickup означає отримання у пункті видачі в місці призначення. Кілька відправлень можуть посилатися на одну картку посилки, але мають різні reference. Календар, маршрути й одночасна обробка не моделюються.

## Персональне правило — знижка постійному клієнту

10% базового тарифу лише для постійного клієнта при тарифі від 100 грн включно. Інакше знижка нульова.

Усі пороги включні, крім явно зазначеного «понад». Гроші — цілі копійки; відсоткова сума округлюється донизу один раз, потім застосовуються мінімум або максимум. Решта ознак, не згаданих у правилі, на розрахунок не впливає. Інших знижок чи доплат немає.

## API

`ShippingService(customers, parcels, shipments, policy)`:

- `calculateBaseFee(weightGrams, distanceKm)` — тариф;
- `calculateDiscount(baseFee, regular)` — персональна функція;
- `calculateRefund(total)` — сума повернення при скасуванні; total — ціле число 0–135000 копійок;
- `createShipment(new ShipmentRequest(reference, customerId, parcelId, distanceKm, urgent=false, pickup=false))` — оформлення;
- `dispatch(id)`, `deliver(id)`, `cancel(id)` — зміни статусів.

Моделі експортуються з src/models.js. Customer(id, code, regular), Parcel(id, code, weightGrams, declaredValue, lengthCm=10, widthCm=10, heightCm=10), Shipment приймає об’єкт із полями збереженого відправлення.

Некоректні входи — TypeError/RangeError; відсутні записи — RangeError; бізнес-відмови — ShipmentRejectedError. Помилки БД передаються виклику.

CustomerRepository і ParcelRepository: create(model), findById(id), update(model), delete(id). ShipmentRepository: create(shipment), findById(id), findShipments(customerId, status), updateStatus(id, expected, next, refund), delete(id). Залежності можна замінити об’єктами з такими самими методами; policy — об’єкт з асинхронним isAllowed.

create повертає модель з id БД, ігноруючи вхідний id. findById повертає null за відсутності запису. findShipments застосовує обидва фільтри одночасно та сортує за id. update відсутнього клієнта/посилки — RangeError. updateStatus перевіряє допустимість переходу та поточний статус: заборонена пара — RangeError, відсутність відповідного запису — ShipmentRejectedError. Видалення відсутнього запису нічого не змінює. Клієнта чи посилку з відправленнями видалити не можна.

Усі методи з БД асинхронні: використовуйте await. Репозиторії отримують відкритий pg.Client; власник закриває його через await client.end(). Оформлення записує один рядок одним атомарним INSERT. Не використовуйте з’єднання паралельно. Для зовнішнього дозволу передайте Stub/Mock або HttpShippingPolicy для перевірки через HTTP.

## Підготовка та запуск

Із папки sut-b:

```sh
npm install
```

У локальній PostgreSQL створіть користувача (один раз) та окрему БД:

```sql
CREATE ROLE delivery_student LOGIN;
\password delivery_student
CREATE DATABASE delivery_variant04_test OWNER delivery_student;
```

Застосуйте міграцію один раз до порожньої БД:

```sh
psql -h localhost -U delivery_student -d delivery_variant04_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
```

Задайте змінні середовища за .env.example; файл .env автоматично не читається. Пароль — DB_PASSWORD.

```sh
npm test
```

Окремо від звичайної перевірки підключення наявний regression suite. Дані для сценаріїв готуйте у власних тестах. Схеми та дані автоматично не створюються й не очищаються. Для незалежності тестів видаляйте власні відправлення перед клієнтами й посилками або використовуйте окрему тестову схему.

## HTTP-політика доставки

`HttpShippingPolicy` реалізує `ShippingPolicy` через вбудований `fetch` Node.js 22. Додаткові пакети не потрібні.

```js
const { HttpShippingPolicy } = require("./src/http-shipping-policy");
const policy = new HttpShippingPolicy(wiremockUrl, 2000);
const service = new ShippingService(customers, parcels, shipments, policy);
```

`wiremockUrl` — базова HTTP(S)-адреса WireMock без шляху, з фактичним портом контейнера. Другий аргумент — таймаут у мілісекундах, ціле число від 1 до 2147483647; охоплює очікування відповіді та читання її тіла.

Після локальних перевірок сервіс надсилає один `POST /shipping-policy` з `Content-Type: application/json`:

```json
{"customerId":1,"parcelId":2,"distanceKm":100}
```

HTTP 200 із `{"allowed":true}` дозволяє зберегти відправлення зі статусом `Registered` і розрахованими сумами. HTTP 200 із `{"allowed":false}` спричиняє `ShipmentRejectedError` без нового запису. Інший статус, некоректний JSON, відсутнє або нелогічне поле `allowed`, мережева помилка чи таймаут спричиняють `ShippingPolicyError`; відправлення також не створюється. Перенаправлення вимкнені; адаптер не реалізує повторних спроб.

Локальна відмова до перевірки політики та зміна статусу відправлення не викликають HTTP-політику. Персональні правила залишаються чинними. У тестах перевіряйте фактичні записи PostgreSQL та кількість і тіло запитів у журналі WireMock.


## REST API

Запуск: `npm install`, потім `npm start` (Node.js 22+).
Потрібна підготовлена PostgreSQL із застосованими міграціями цього варіанта.
Підключення задають `DB_HOST`, `DB_PORT`, `DB_NAME` (типово `delivery_variant04_test`), `DB_USER` (типово `delivery_student`), `DB_PASSWORD`.
Адреса API: `http://127.0.0.1:8080`. Порт можна змінити через `API_PORT`.
Змінні середовища потрібно задати перед запуском; файл `.env.example` є лише зразком.

| Метод | Шлях | Результат |
|---|---|---|
| POST | `/customers` | Створений клієнт, 201 та Location |
| GET | `/customers/{id}` | Клієнт із БД, 200 |
| POST | `/parcels` | Створена посилка, 201 та Location |
| GET | `/parcels/{id}` | Посилка з БД, 200 |
| POST | `/shipments` | Створене через сервіс відправлення, 201 та Location |
| GET | `/shipments/{id}` | Збережене відправлення, 200 |
| POST | `/shipments/{id}/dispatch` | Відправлення передано в доставку, 200 |
| POST | `/shipments/{id}/deliver` | Доставку завершено, 200 |
| POST | `/shipments/{id}/cancel` | Відправлення скасовано, 200 |

Приклади JSON для POST (`Content-Type: application/json`):

- Клієнт: `{"code": "C-001", "regular": false}`.
- Посилка: `{"code": "P-001", "weightGrams": 1000, "declaredValue": 10000, "lengthCm": 10, "widthCm": 10, "heightCm": 10}`.
- Відправлення: `{"reference": "S-001", "customerId": 1, "parcelId": 1, "distanceKm": 100, "urgent": false, "pickup": false}`.

Підставляйте ідентифікатори з відповідей створення клієнта та посилки. Дії `dispatch`, `deliver`, `cancel` виконуються без тіла запиту.
Суми — у копійках; вага — у грамах; відстань — у кілометрах.
Персональне правило з попереднього опису залишається чинним: перевіряйте через GET розраховані суми та збережений статус після дії.
Статуси: `Registered`, `Dispatched`, `Delivered`, `Cancelled`. Недозволений перехід або бізнес-відмова повертає 409; відсутній ресурс — 404; некоректний запит — 400.
Помилки мають вигляд `{"code":"...","message":"..."}`.

`SHIPPING_POLICY_URL` підключає наявний HTTP-клієнт зовнішньої перевірки. Без цієї змінної локальна політика дозволяє операції; бізнес-обмеження сервісу продовжують діяти.
Недоступна зовнішня перевірка повертає 502. API не застосовує міграції та не очищає БД автоматично.


## UI та окремий regression suite

Готовий UI розташований у сусідній папці [sut-c-ui](../sut-c-ui/README.md).
Він доступний після звичайного запуску цього backend на /index.html; окрема збірка frontend не потрібна.
Запускайте backend із папки sut-b. Порт за замовчуванням — 8080.

Regression suite — окремий навчальний набір із навмисними проблемами стабільності.
Для його запуску потрібен Docker; PostgreSQL піднімається через Testcontainers, міграції застосовуються набором.
Команда з цієї папки:

```sh
npm run regression
```

Звичайні тести та цей окремий набір мають різні умови запуску.
Студентські тести повинні перевіряти вимоги та фактичний стан системи; повторні запуски мають бути незалежними.
Для security testing використовуйте окремі vulnerable-копії, а не цей SUT.
