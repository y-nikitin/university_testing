## Промпт для AI-агента

Створи в цій папці невеликий працездатний SUT на Java для бронювання готелю. Працюй тільки в поточній папці `sut-b`; не змінюй сусідній `sut-a` та інші варіанти. Якщо файли вже існують, спочатку перевір їх і доповни наявну реалізацію без втрати роботи студента.

### Стек і межі

- Java 21+, Maven, PostgreSQL 17, JDBC, JUnit 5; тестові двійники через Mockito або власні реалізації.
- Реальні SQL-репозиторії без ORM. Параметризовані запити; жодної конкатенації користувацьких значень у SQL.
- Один сервіс, два репозиторії з інтерфейсами та одна зовнішня залежність. Невеликі record-моделі й enum.
- Не додавай HTTP API, UI, Docker, Testcontainers, CI/CD, авторизацію, мережеві зовнішні сервіси, фонові процеси та навмисні дефекти.
- Не генеруй навчальні unit/integration-тести, звіти, coverage чи mutation-конфігурації. Допускається лише один тест доступності БД.
- Усі пояснення, коментарі й повідомлення помилок — українською. Ідентифікатори коду — англійською.

### Модель і БД

Створи рівно три таблиці:

1. `rooms`: згенерований BIGINT `id` PRIMARY KEY; непорожній `number` VARCHAR(10) NOT NULL UNIQUE; `capacity` INTEGER 1–4; `nightly_price` BIGINT 100–10 000 000 копійок.
2. `booking_status`: `code` PRIMARY KEY, `title` NOT NULL UNIQUE. Значення CONFIRMED («Підтверджено») та CANCELLED («Скасовано»).
3. `bookings`: згенерований `id`; непорожній унікальний `reference` VARCHAR(40); `room_id` FOREIGN KEY на rooms; `nights` INTEGER 1–30; `guests` INTEGER 1–4; `total` BIGINT >= 0; `status` FOREIGN KEY на booking_status. Усі поля NOT NULL.

Числові межі забезпеч CHECK-constraints. Зовнішні ключі — ON DELETE RESTRICT. Додай індекс `(room_id, status)`. Один номер може мати багато бронювань; видалення номера з бронюваннями заборонено.

Моделі: `Room`, `Booking`, `BookingStatus`; заявка `BookingRequest(reference, room_id, nights, guests)`.

Два SQL-файли міграцій: створення таблиць та заповнення двох статусів. Одноразове застосування до порожньої тестової БД. Бізнес-дані не додавай: номери та бронювання створюють тести.

### Репозиторії

`RoomRepository`:

- `create(number, capacity, nightly_price) -> Room`;
- `findById(id) -> Room | null`;
- `update(room) -> void`;
- `delete(id) -> void`.

`BookingRepository`:

- `create(booking) -> long`: повертає згенерований id, ігнорує вхідний id, зберігає решту полів;
- `findById(id) -> Booking | null`;
- `findAll() -> List<Booking>`: за зростанням id;
- `updateStatus(id, status) -> void`;
- `delete(id) -> void`;
- `findByRoomAndStatus(room_id, status) -> List<Booking>`.

Оновлення відсутнього запису спричиняє IllegalArgumentException; видалення відсутнього запису нічого не змінює. Помилки constraints передаються як SQLException. Обидва репозиторії отримують відкрите з’єднання через конструктор; закриває його власник. Курсори закривай після операцій. Використовуй auto-commit: кожна операція сервісу виконує один запис у БД.

### Зовнішня залежність

`BookingPolicy.isAllowed(room: Room, nights: int, guests: int) -> boolean` — інтерфейс, який передається сервісу через конструктор. Реальної реалізації з I/O не створюй. Тести задаватимуть true, false або виняток. Результат має тип boolean.

### Сервіс і правила

`BookingService` отримує два репозиторії та BookingPolicy.

`createBooking(request) -> Booking`:

1. До викликів залежностей перевір заявку: reference обов’язковий, не порожній і не лише пробіли, до 40 символів; room_id — додатний int; nights — int 1–30; guests — int 1–4. Типи числових і логічних полів визначаються сигнатурами. Некоректний вхід або відсутня заявка — IllegalArgumentException.
2. Прочитай номер. Якщо він відсутній — IllegalArgumentException.
3. Якщо гостей більше за capacity — BookingRejectedException.
4. Виклич один раз BookingPolicy з прочитаним номером, строком та кількістю гостей. false — BookingRejectedException; виняток залежності передається виклику. В обох випадках бронювання не створюється.
5. Базова сума — nightly_price × nights. Від 7 ночей включно знижка 5%; округли суму знижки донизу до копійки й відніми від базової суми.
6. Збережи один запис CONFIRMED, поверни Booking зі згенерованим id. Помилку збереження не приховуй.

`cancelBooking(id) -> Booking`:

- id — додатний int; некоректний id або відсутнє бронювання — IllegalArgumentException;
- повторне скасування — BookingRejectedException;
- зміни тільки статус на CANCELLED і поверни оновлений об’єкт;
- сума, строк та кількість гостей не змінюються; BookingPolicy не викликається.

Створи окремий клас BookingRejectedException. Дотримуйся порядку перевірок. Дати, зайнятість номера на конкретний період, лояльність, сніданки, оплата й конкурентні запити не входять у модель. Кілька бронювань одного номера дозволені; номер не має змінного статусу зайнятості.

### Custom query

Реалізуй `findByRoomAndStatus` одразу разом із SUT. Обидві умови обов’язкові: room_id та status мають одночасно збігатися. Поверни всі збіги за зростанням id або порожній список. room_id — додатний int; status — BookingStatus. Некоректні аргументи спричиняють IllegalArgumentException до виконання SQL. Використовуй параметризований запит та спільне перетворення рядків на Booking.

### Запуск і подальше розширення

Додай мінімальну конфігурацію залежностей, `.gitignore` для кешу, файлів збірки та секретів, `database-test.properties` без пароля та перевизначення через DB_URL, DB_USER, DB_PASSWORD. Не зберігай справжні паролі.

В окремому короткому `SETUP.md` поясни встановлення інструментів та залежностей, створення окремої локальної БД, застосування міграцій та запуск mvn test. Зазнач, що кожен тест сам створює й очищає свої бізнес-дані; автоматично очищати всю налаштовану БД заборонено.

Не прив’язуй репозиторії до конкретного порту або адреси. Ті самі міграції й параметри підключення повинні дозволяти згодом використати тимчасову PostgreSQL без зміни бізнес-коду. Інструменти наступних робіт наперед не додавай.

Перевір компіляцію проєкту. Якщо окрема тестова БД уже явно надана студентом, перевір підключення й застосування міграцій у порожній тестовій схемі. Не використовуй сторонні БД і не приховуй відсутність середовища: повідом, що саме перевірено та що студент має налаштувати. Не встановлюй системну СУБД автоматично.


Очікування для власних тестів визначайте за цією специфікацією. Дані мають містити записи, що відповідають обом умовам фільтра, лише одній або жодній. Перевіряйте точний склад результатів. Помилки реалізації виправляють у коді, а не зміною вимог.

Ідентифікатори SQL зберігай у snake_case. У коді дотримуйся camelCase для методів і полів Java; ідентифікатори БД та суми — long, лічильники — int. Для відсутнього запису findById повертає null.
