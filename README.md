# Тестування та верифікація ПЗ

Репозиторій містить навчальні варіанти для перших трьох лабораторних робіт. Кожен варіант — окрема невелика система під тестуванням (SUT) із власною предметною областю та бізнес-правилами. Варіанти незалежні й не утворюють одного застосунку.

## Поточний стан

Для всіх варіантів підготовлено українські специфікації у файлах `README.md`. У папках варіантів наразі є лише специфікації: бізнес-код, засоби запуску, тести та конфігурації інструментів ще не додано.

У локальній папці `teacher/` є докладний `README.md` та компактна сторінка `answers.html` із вимогами й 15 рекомендованими тест-кейсами на кожну тему. Матеріали викладача спільні для підгруп і виключені з Git правилом `/teacher/`.

group 317/
  variant01/ … variant03/

У підгрупах 1–4 є по 18 варіантів, у `group 317` — перші 3. Однаковий номер у різних підгрупах відповідає тій самій темі та специфікації.

## Як знайти свій варіант

1. Відкрийте папку своєї підгрупи.
2. Оберіть варіант за **порядковим номером у підгрупі, а не в академічній групі**.
3. Прочитайте `README.md` усередині папки варіанта.

Наприклад, студент №7 у другій підгрупі працює з `group 2/variant07/README.md`.

Номери можуть повторюватися між підгрупами. Обмінюватися варіантами всередині підгрупи не дозволяється. Для всіх трьох лабораторних робіт зберігається той самий варіант.

## Мова програмування

Студент обирає мову: **Java, Python, C# або JavaScript**. Мова не закріплена за номером варіанта й не змінює його тему. Наприклад, варіант 01 залишається бронюванням готелю незалежно від обраної мови.

Готову реалізацію SUT відповідною мовою надає викладач. Студент виконує тест-дизайн і пише власні тести. Мовні версії однієї теми мають відповідати спільним вимогам і бути зіставними за складністю. Вибір мови не впливає на оцінювання.

## Лабораторна робота №1 — Тестування чорної скриньки

Студент працює за специфікацією та зовнішньою поведінкою SUT, **без перегляду вихідного коду**. README варіанта визначає входи, допустимі значення, бізнес-правила, результати та помилки.

Результат роботи — документ, який містить:

- аналіз вимог;
- класи еквівалентності з представниками;
- граничні значення;
- таблицю рішень;
- одну додаткову техніку: попарне тестування, переходи станів або сценарне тестування;
- 12–15 обґрунтованих тест-кейсів.

На захисті потрібно вручну виконати 2–3 тест-кейси. Засіб запуску та інструкцію введення даних буде додано разом із реалізацією. Наразі можна проєктувати тести за вимогами, але виконати їх на SUT ще неможливо. Автоматизовані тести для цієї роботи не потрібні.

## Лабораторна робота №2 — Модульне тестування та тестові двійники

Починаючи з цієї роботи, вихідний код можна й потрібно аналізувати. Студент тестує той самий SUT, ізолюючи його залежності.

Очікується набір із щонайменше 8–10 змістовних unit-тестів: позитивні, негативні та помилкові сценарії, параметризація на 4–6 наборах, перевірки результатів і взаємодій. Обов’язкова перевірка аргументів, переданих залежності. Тести та налаштування тестового фреймворку виконує студент; окремий розгорнутий текстовий звіт не потрібний.

## Лабораторна робота №3 — Покриття та мутаційне тестування

Використовуються той самий SUT і тести з попередньої роботи. Студент аналізує покриття рядків і гілок, результати мутаційного тестування та вдосконалює тестовий набір. Покриття й мутації не входять до перших двох лабораторних.

## Запуск та інструменти

Команд збирання, запуску, виконання тестів, отримання покриття й мутаційного аналізу поки немає. Інструкції додаватимуться для конкретних мовних реалізацій. Поточні папки варіантів не прив’язані до структури певного фреймворку.

## Межі навчальних систем

Перші три лабораторні зосереджені на бізнес-логіці, тестових двійниках, покритті та мутаціях. Реальні бази даних, REST API, мережеві інтеграції, робота з файлами, графічний інтерфейс SUT, Docker і CI/CD до цього етапу не входять. Інтеграційні тести не є завданням перших двох робіт.

Документація та коментарі до коду — українською. Назви класів, методів і змінних — англійською.
