# Тестування та верифікація ПЗ

Навчальні системи під тестуванням для курсу «Тестування та верифікація ПЗ». Кожен варіант — незалежний проєкт. Єдиної команди запуску всього репозиторію немає.

## Вибір варіанта

Оберіть папку своєї підгрупи та `variantXX` за **порядковим номером у підгрупі, а не в академічній групі**. Номери можуть повторюватися між підгрупами; обмінюватися варіантами всередині підгрупи не дозволяється.

| Підгрупа | Реалізовані варіанти | Тематика SUT B/C |
|---|---|---|
| [group 1](group%201/) | 01–18 | Навчальні курси |
| [group 2](group%202/) | 01–18 | Доставка |
| [group 3](group%203/) | 01–17 | Оренда |
| [group 4](group%204/) | 01–17 | Магазин |
| [group 317](group%20317/) | 01–03 | Готель |

Загалом — 73 реалізовані варіанти. `variant18` у групах 3 і 4 містять попередні матеріали без готового SUT B.
Мови: Java, Python, C#, JavaScript і Go. У групі 3 варіанти 02 і 05 реалізовано на Go. Використовуйте мову свого проєкту.

## Структура варіанта

```text
group N/variantXX/
  README.md
  sut-a/
  sut-b/
  sut-c-ui/
  sut-b-vulnerable/
  sut-c-vulnerable/
```

| Частина | Призначення |
|---|---|
| SUT A | Специфікація та бізнес-код для чорної скриньки, unit-тестів, тестових двійників, покриття й мутацій |
| SUT B | REST API, сервіс, репозиторії PostgreSQL, міграції, зовнішня HTTP-політика та regression suite |
| SUT C UI | Готовий вебінтерфейс до SUT B для UI/E2E-тестування |
| SUT B vulnerable | Окрема навмисно вразлива версія backend |
| SUT C vulnerable | Окрема навмисно вразлива версія UI |

SUT A має власні вимоги. Вимоги SUT A не переносяться автоматично на SUT B. Джерело очікуваної поведінки та персонального правила — README відповідного SUT.

**Лабораторну №1 виконуйте без перегляду коду SUT A. Аналізувати код можна починаючи з лабораторної №2.**

## Запуск SUT B та UI

1. Відкрийте README свого варіанта, потім `sut-b/README.md`.
2. Встановіть залежності відповідно до мови проєкту.
3. Підготуйте PostgreSQL, застосуйте готові міграції та задайте параметри `DB_*` за інструкцією SUT B.
4. Запустіть backend із папки `sut-b`.

| Мова | Типова команда запуску |
|---|---|
| Java | `mvn spring-boot:run` |
| Python | `python -m uvicorn <модуль>.api:app --host 127.0.0.1 --port 8080` |
| C# | `dotnet run` |
| JavaScript | `npm start` |
| Go | `go run ./cmd/api` |

Для Python замість `<модуль>` використайте назву з README проєкту: `courses`, `delivery`, `rental`, `store` або `hotel`.

Відкрийте **http://127.0.0.1:8080/index.html**. Якщо змінено порт, використайте його. Backend віддає сусідню папку `sut-c-ui`; окремий frontend-сервер не потрібен. Збережіть розташування цих папок. Відкриття HTML через `file://` не замінює запуск системи.

Звичайний запуск API не створює та не очищає БД і не застосовує міграції автоматично. Не припускайте автоматичне читання `.env`: дотримуйтеся конфігурації конкретного проєкту.

## Тести

Команди й залежності наведені в README конкретного SUT. Для SUT A студент налаштовує тестове середовище, покриття та мутаційне тестування відповідно до мови. Готових розв’язків лабораторних для всіх варіантів немає.

У SUT B є окремий **regression suite з навмисними проблемами стабільності**. Він використовує Docker і PostgreSQL через Testcontainers; міграції застосовує сам набір.

| Мова | Запуск regression із папки SUT B |
|---|---|
| Java | `mvn -Pregression test` |
| Python | `python -m pytest tests/<назва>_regression.py` |
| C# | `dotnet test tests/regression/<назва>.Regression.csproj` |
| JavaScript | `npm run regression` |
| Go | `go test -tags=regression -count=1 -v ./...` |

Точні назви файлів і команди встановлення залежностей дивіться у README SUT B. Звичайні перевірки підключення та regression suite мають різні умови запуску. Падіння навмисно проблемного набору — матеріал для аналізу; smoke-підмножину й виправлення студент готує самостійно.

## HTTP та E2E

SUT B містить HTTP-адаптер зовнішньої політики, який можна підключити до WireMock через конфігурацію свого проєкту. Testcontainers-середовище та потрібні інтеграційні сценарії студент налаштовує відповідно до завдання.

SUT C використовує реальний API. E2E-сценарій проходить шлях **браузер → UI → API → сервіс → репозиторій → БД**. Перевіряйте видимий результат операції та персональне правило варіанта. UI-тести студент пише самостійно.

## Security testing

Використовуйте `sut-b-vulnerable` разом із `sut-c-vulnerable`. Це окремі навчальні копії з навмисними вразливостями.

Запускайте їх локально з вигаданими даними й окремою БД. Параметри підключення — `SECURITY_DB_*`; типовий порт API — **8082**, PostgreSQL — **55433**. Точні команди наведені в README vulnerable-проєкту. Для Python використовуйте окреме віртуальне середовище.

Regression suite звичайного SUT B до vulnerable-копій не переноситься. Не використовуйте для security-сценаріїв БД звичайного SUT B.
