# Навчальні варіанти для дисципліни «Тестування та верифікація ПЗ»

Репозиторій призначений для 18 незалежних невеликих систем під тестуванням (SUT). Кожен варіант матиме власну предметну область, бізнес-правила та специфікацію. Варіанти не утворюють спільного застосунку й мають бути приблизно однаковими за складністю.

Один і той самий варіант використовується послідовно для трьох лабораторних робіт:

1. **Проєктування тестів методом «чорної скриньки».** Аналіз вимог, класи еквівалентності, граничні значення, таблиці рішень і додаткова техніка тест-дизайну.
2. **Модульне тестування та тестові двійники.** Перевірка бізнес-логіки, параметризовані тести, ізоляція залежностей, перевірка результатів і взаємодій.
3. **Покриття коду та мутаційне тестування.** Аналіз повноти й ефективності тестів на тому самому коді.

## Поточний стан

Наразі створено структуру папок і окремий `README.md` зі специфікацією для кожного з 18 варіантів. У Python-варіантах додано порожні файли `__init__.py`, які позначають пакети.

Бізнес-логіку, матеріали викладача, тести та конфігурації інструментів ще не додано. Команд збирання, запуску, перевірки покриття й мутаційного тестування на цьому етапі немає. Можливість запуску буде додана пізніше.

## Структура репозиторію

```text
README.md
src/
  variant01/ … variant05/    — Java
  variant06/ … variant10/    — Python
  variant11/ … variant14/    — C#
  variant15/ … variant18/    — JavaScript
teacher/                    — матеріали викладача
```

Кожна папка `src/variantXX/` є окремим варіантом. Усередині підготовлено структуру для відповідної мови:

| Мова | Розташування вихідного коду відносно папки варіанта |
|---|---|
| Java | `src/main/java/ua/edu/testing/variantXX/` |
| Python | `src/variantXX/` |
| C# | `src/VariantXX/` |
| JavaScript | `src/` |

Позначення `XX` означає двозначний номер варіанта. Специфікації розміщено у файлах `src/variantXX/README.md`, а пояснення для викладача плануються у `teacher/variantXX-solution.md`.

## Вибір варіанта

Номер варіанта відповідає **порядковому номеру студента у своїй підгрупі, а не в академічній групі**. Наприклад, студент із номером 7 у підгрупі працює з `src/variant07/`.

- Номери варіантів можуть повторюватися в різних підгрупах.
- Обмінюватися варіантами всередині однієї підгрупи не дозволяється.
- Для всіх трьох лабораторних робіт зберігається той самий варіант.
- Мова програмування визначається варіантом і не впливає на оцінювання.

## Порядок роботи

**Лабораторна робота №1** виконується за специфікацією та зовнішньою поведінкою SUT, без перегляду вихідного коду. Студент самостійно визначає техніки тест-дизайну й формує 12–15 тест-кейсів. Автоматизовані тести на цьому етапі не потрібні.

**Починаючи з лабораторної роботи №2**, вихідний код можна й потрібно аналізувати. Студент створює власні модульні тести та ізолює залежності тестованого компонента за допомогою тестових двійників. Готові студентські розв’язання не передбачені.

**У лабораторній роботі №3** використовуються той самий SUT і тести з попередньої роботи. Студент аналізує покриття та результати мутаційного тестування й удосконалює тестовий набір.

## Межі навчальних систем

Варіанти зосереджені на бізнес-логіці. Заплановано невеликі сервіси з класами даних і залежностями, які можна замінювати тестовими двійниками без зміни основної архітектури.

Бази даних, REST API, мережеві інтеграції, робота з файлами, графічний інтерфейс, Docker і CI/CD до цього етапу не входять. Усі Markdown-документи й коментарі до коду оформлюються українською; назви класів, методів і змінних — англійською.
