# SUT B — Прокат обладнання, варіант 11

C#, .NET 8 SDK, PostgreSQL 17, Npgsql, xUnit та Moq.

## Поведінка

Обладнання має унікальний непорожній код до 40 символів, добову ціну 100–1 000 000 копійок та невід’ємний залишок. Одна оренда містить один вид обладнання: 1–20 одиниць на 1–30 днів включно. Код оренди унікальний, непорожній, до 40 символів. Ідентифікатори у заявках додатні.

Оформлення перевіряє заявку, існування обладнання та залишок, після чого один раз викликає IRentalPolicy.IsAllowed. Відмова або виняток припиняє оформлення без запису. Успіх створює оренду Active та її позицію атомарно. Сума — добова ціна × кількість × дні. Ціна фіксується в позиції; подальші зміни обладнання не змінюють розрахунків оренди. Залишок перевіряється, але не зменшується й не відновлюється.

Повернення змінює Active на Returned і зберігає доплату. Повторне повернення заборонене. Початкова сума оренди залишається незмінною; сукупна сума — Total + LateFee. При поверненні зовнішня залежність не викликається.

## Персональна функція: доплата за прострочення

Прострочення задається цілим числом днів 0–36500. При 0 або 1 дні доплата нульова. За кожен день після першого доплата становить 10% добової вартості всіх орендованих одиниць. Спочатку рахується загальна доплата, потім вона округлюється донизу до цілої копійки. Максимум — початкова сума оренди.

Наприклад: 2 одиниці по 100 грн на добу орендовано на 3 дні. Початкова сума — 600 грн. При простроченні на 4 дні доплата — 60 грн; на 31 день — 600 грн; на 32 дні — також 600 грн.

Календар, платежі та паралельне оформлення не моделюються.

## API

`RentalService(equipmentRepository, rentalRepository, policy)`:

- `CalculateTotal(dailyRate, quantity, days)` — початкова сума;
- `CalculateLateFee(dailyRate, quantity, rentalDays, overdueDays)` — персональний розрахунок;
- `Rent(new RentalRequest(reference, equipmentId, quantity, days))` — оформлення;
- `ReturnRental(id, overdueDays)` — повернення із записом доплати.

Некоректні входи або відсутні записи — ArgumentException чи його підтипи; бізнес-відмови — RentalRejectedException. Помилки БД передаються виклику.

EquipmentRepository: Create, FindById, Update, Delete. RentalRepository: Create, FindById, FindRentals(equipmentId, status), MarkReturned, Delete. Обидва реалізують інтерфейси для тестових двійників. Create повертає модель з ідентифікаторами БД, ігноруючи вхідні id. FindById повертає null за відсутності запису. FindRentals застосовує обидві умови одночасно, результат упорядкований за id. Update відсутнього обладнання викликає ArgumentException; MarkReturned відсутньої чи повернутої оренди — RentalRejectedException. Delete відсутнього запису нічого не змінює. Видалення оренди каскадно видаляє позицію; обладнання з позиціями видалити не можна.

Репозиторії отримують одне відкрите з’єднання. Власник закриває його через using. Create оренди використовує власну транзакцію; не обгортайте його у зовнішню транзакцію і не використовуйте з’єднання паралельно. Для IRentalPolicy можна передати Stub/Mock або HttpRentalPolicy для перевірки через HTTP.

## Підготовка та запуск

Створіть навчального користувача й окрему БД у локальній PostgreSQL:

```sql
CREATE ROLE rental_student LOGIN;
\password rental_student
CREATE DATABASE rental_variant11_test OWNER rental_student;
```

Із папки sut-b застосуйте міграцію один раз до порожньої БД:

```sh
psql -h localhost -U rental_student -d rental_variant11_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
```

Задайте змінні середовища за .env.example. Файл .env автоматично не читається. Пароль задається через DB_PASSWORD.

```sh
dotnet build Rental.csproj
dotnet test tests/Rental.Tests.csproj
```

Окремо від звичайної перевірки підключення наявний regression suite. Дані для бізнес-сценаріїв готуйте у власних тестах. Автоматичного створення або видалення схем немає. Для незалежності тестів видаляйте власні оренди перед обладнанням або використовуйте окрему тестову схему.

## HTTP-політика оренди

`HttpRentalPolicy` реалізує `IRentalPolicy` через HTTP. Адреса та таймаут передаються конструктору; додаткових пакетів не потрібно.

```csharp
using var policy = new HttpRentalPolicy(new Uri(wireMockUrl), TimeSpan.FromSeconds(2));
var service = new RentalService(equipmentRepository, rentalRepository, policy);
```

`wireMockUrl` — базова адреса WireMock з фактичним портом, наприклад адреса, отримана від контейнера. Власник політики звільняє її після завершення всіх викликів сервісу.

Після перевірки заявки, існування обладнання та залишку сервіс надсилає один `POST /rental-policy` з `Content-Type: application/json`:

```json
{"equipmentId":1,"quantity":2,"days":7}
```

HTTP 200 із `{"allowed":true}` дозволяє створити оренду та позицію в БД. HTTP 200 із `{"allowed":false}` спричиняє `RentalRejectedException` без створення записів. Інший HTTP-статус, некоректний JSON, відсутнє або нелогічне поле `allowed`, мережева помилка чи таймаут спричиняють `RentalPolicyException`; записів також немає. Перенаправлення не виконуються; автоматичних повторів на рівні адаптера немає.

Локальна відмова до перевірки політики не надсилає HTTP-запит. Повернення оренди також не звертається до HTTP-політики. У тестах можна перевіряти стан оренди й позиції в PostgreSQL та кількість і тіло запитів у журналі WireMock.

## REST API через ASP.NET Core

Потрібен .NET 8 SDK. Підготуйте локальну тестову PostgreSQL та застосуйте наявну міграцію. Задайте DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD за попередніми інструкціями. Із папки sut-b:

```sh
dotnet run --project Rental.csproj
```

API: `http://127.0.0.1:8080`; порт задається API_PORT. Зупинка — Ctrl+C. Міграції автоматично не виконуються, файл .env автоматично не читається.

| Метод і шлях | Результат |
|---|---|
| `POST /equipment` | Створення обладнання, `201` і Location |
| `GET /equipment/{id}` | Обладнання, `200`; відсутнє — `404` |
| `POST /rentals` | Оформлення оренди, `201` і Location |
| `GET /rentals/{id}` | Оренда, `200`; відсутня — `404` |
| `POST /rentals/{id}/return` | Повернення з доплатою, `200`; повторне — `409` |

Обладнання:

```json
{"code":"API-E1","dailyRate":10000,"stock":10}
```

Оренда з отриманим equipmentId:

```json
{"reference":"API-R1","equipmentId":1,"quantity":2,"days":3}
```

Відповідь містить id, reference, days, total, lateFee, status і item із id, equipmentId, quantity, dailyRate. Гроші — копійки. Приклад дає total=60000, lateFee=0, status=Active.

Повернення потребує JSON:

```json
{"overdueDays":4}
```

Результат: Returned, lateFee=6000, total=60000. Персональне правило збережене: перший день прострочення безкоштовний; далі 10% добової вартості всіх одиниць за день, максимум — початкова сума оренди.

Без RENTAL_POLICY_URL локальна зовнішня політика дозволяє оформлення. Для WireMock задайте цю змінну базовою адресою контейнера; використовується HttpRentalPolicy з контрактом POST /rental-policy. Авторизації немає.

Помилки містять code і message: `404 / NOT_FOUND`, `409 / RENTAL_CONFLICT`, дубль коду — `409 / DUPLICATE_RESOURCE`, некоректні дані — `400 / INVALID_REQUEST`, збій HTTP-політики — `502 / POLICY_UNAVAILABLE`, помилка БД — `500 / DATABASE_ERROR`.

Сервіс і репозиторії реєструються через AddScoped. Один HTTP-запит використовує одне відкрите з’єднання; ASP.NET Core закриває його після запиту. Створення оренди та позиції залишається атомарним. Залишок обладнання лише перевіряється, не зменшується.

API не очищає дані після зупинки. Кожен незалежний тест створює власне обладнання та унікальний reference; результат перевіряється наступним GET. Навчальні сценарії виконуйте послідовно. Попередні тести можна запускати як раніше; готові API-тести не додаються.


## UI та окремий regression suite

Готовий UI розташований у сусідній папці [sut-c-ui](../sut-c-ui/README.md).
Він доступний після звичайного запуску цього backend на /index.html; окрема збірка frontend не потрібна.
Запускайте backend із папки sut-b. Порт за замовчуванням — 8080.

Regression suite — окремий навчальний набір із навмисними проблемами стабільності.
Для його запуску потрібен Docker; PostgreSQL піднімається через Testcontainers, міграції застосовуються набором.
Команда з цієї папки:

```sh
dotnet test tests/regression/Rental.Regression.csproj
```

Звичайні тести та цей окремий набір мають різні умови запуску.
Студентські тести повинні перевіряти вимоги та фактичний стан системи; повторні запуски мають бути незалежними.
Для security testing використовуйте окремі vulnerable-копії, а не цей SUT.
