# SUT B — Прокат обладнання, варіант 01

Python 3.12+, PostgreSQL 17, psycopg та pytest.

## Поведінка

Обладнання має унікальний непорожній код до 40 символів, добову ціну 100–1 000 000 копійок та невід’ємний залишок. Одна оренда містить один вид обладнання: 1–20 одиниць на 1–30 днів включно. Код оренди унікальний, непорожній, до 40 символів. Ідентифікатори заявок — додатні цілі до 2⁶³−1. Логічні значення не допускаються замість чисел; premium — лише bool.

Оформлення перевіряє заявку, існування обладнання, залишок і персональні умови дозволу. Потім один раз викликає RentalPolicy.is_allowed(equipment, quantity, days). False означає відмову, значення іншого типу — ValueError. Виняток зовнішньої перевірки передається виклику. В усіх цих випадках оренда не записується.

Успіх атомарно створює оренду Active і позицію зі знімком добової ціни. Сума — ціна × кількість × дні мінус персональна знижка, якщо вона передбачена. Преміальність зберігається в оренді. Подальші зміни обладнання не змінюють розрахунків. Залишок перевіряється, але оформлення й повернення його не змінюють.

Повернення змінює Active на Returned і записує доплату. Повторне повернення заборонене. Початкова сума total не змінюється; сукупна сума — total + late_fee. Зовнішня перевірка при поверненні не викликається. Прострочення — ціле число 0–36500 днів.

## Персональне правило

Знижка 10% при оренді від 7 днів включно. Преміальність не впливає на знижку.

Усі межі включні. Гроші — цілі копійки. Загальна сума знижки чи доплати округлюється донизу один раз, після розрахунку за всі одиниці та дні. Якщо персональне правило не передбачає знижки або доплати, відповідна сума нульова. Якщо правило не обмежує дозвіл, достатньо загальних перевірок і зовнішнього дозволу. Календар, платежі та паралельне оформлення не моделюються.

## API

`RentalService(equipment, rentals, policy)`:

- `calculate_total(daily_rate, quantity, days, premium=False)` — початкова сума з урахуванням знижки;
- `calculate_late_fee(daily_rate, quantity, days, overdue_days, premium=False)` — доплата;
- `is_rental_allowed(daily_rate, quantity, days, premium=False)` — персональні умови дозволу; залишок і зовнішню перевірку перевіряє rent;
- `rent(RentalRequest(reference, equipment_id, quantity, days, premium=False))` — оформлення;
- `return_rental(rental_id, overdue_days)` — повернення з доплатою за даними збереженої оренди.

Некоректні входи та відсутні записи — ValueError; бізнес-відмови — RentalRejectedError. Помилки БД передаються виклику.

PostgresEquipmentRepository: create(Equipment), find_by_id, update(Equipment), delete. PostgresRentalRepository: create(RentalOrder), find_by_id, find_rentals(equipment_id, status), mark_returned(rental_id, late_fee), delete. Контракти залежностей містяться у rental/ports.py для Stub, Mock, Spy та Fake.

create повертає модель з ідентифікаторами БД, ігноруючи вхідні id. find_by_id повертає None за відсутності запису. find_rentals застосовує обидва фільтри одночасно, повертає список за зростанням id. update відсутнього обладнання — ValueError; mark_returned відсутньої чи повернутої оренди — RentalRejectedError. Видалення відсутнього запису нічого не змінює. Видалення оренди каскадно видаляє позицію; обладнання з позиціями видалити не можна.

Репозиторії отримують відкрите з’єднання від rental.database.connect з autocommit=True. Власник закриває його через with. create оренди використовує власну транзакцію; не обгортайте його в зовнішню транзакцію та не використовуйте з’єднання паралельно. Для RentalPolicy передайте тестовий двійник або HttpRentalPolicy для перевірки через HTTP.


Створіть навчального користувача (один раз) і окрему БД у локальній PostgreSQL:

Є лише тест підключення. Дані для бізнес-сценаріїв готуйте у власних тестах. Автоматичного створення або видалення схем немає. Для незалежності тестів очищайте власні оренди перед обладнанням або використовуйте окрему тестову схему.

## HTTP-політика оренди

`HttpRentalPolicy` реалізує контракт `RentalPolicy` через HTTP засобами стандартної бібліотеки Python; додаткові пакети не потрібні.

```python
from rental.http_rental_policy import HttpRentalPolicy

policy = HttpRentalPolicy(wiremock_url, timeout=2)
service = RentalService(equipment_repository, rental_repository, policy)
```

`wiremock_url` — базова HTTP(S)-адреса без шляху, з фактичним портом WireMock, отриманим під час запуску контейнера. `timeout` — додатний скінченний час очікування операцій сокета в секундах.

Після локальних перевірок сервіс надсилає один `POST /rental-policy` з `Content-Type: application/json`:

```json
{"equipmentId":1,"quantity":2,"days":7}
```

HTTP 200 із `{"allowed":true}` дозволяє створення оренди та її позиції в БД. HTTP 200 із `{"allowed":false}` спричиняє `RentalRejectedError` без записів. Інший HTTP-статус, некоректний JSON, відсутнє або нелогічне поле `allowed`, мережева помилка чи таймаут спричиняють `RentalPolicyError`; оренда та позиція не створюються. Перенаправлення й автоматичні повтори не виконуються; з’єднання закривається після кожного виклику.

Некоректна заявка, недостатній залишок або невиконання персональних умов зупиняють операцію до HTTP-запиту. Повернення оренди не викликає HTTP-політику. У тестах перевіряйте стан PostgreSQL та кількість і тіло запитів у журналі WireMock. Персональні правила розрахунків і дозволу залишаються чинними.
