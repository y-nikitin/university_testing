# SUT B — Бронювання квитків у кіно

Ця папка призначена для окремого мініпроєкту на Python. Його очікувану поведінку визначає специфікація нижче. Код і дефекти SUT A не потрібно переносити сюди.

Передайте своєму AI-агенту: **«Виконай промпт із README.md у папці sut-b»**. Після створення перевірте запуск і збережіть початкову версію SUT у Git. Власні навчальні тести додавайте окремо. Цей README залиште незмінним як джерело вимог.

## Промпт для AI-агента

Створи в цій папці невеликий працездатний SUT на Python для бронювання квитків у кіно. Працюй тільки в поточній папці `sut-b`; не змінюй сусідній `sut-a` та інші варіанти. Якщо файли вже існують, спочатку перевір їх і доповни наявну реалізацію без втрати роботи студента.

### Стек і межі

- Python 3.12+, PostgreSQL 17, psycopg 3, pytest; тестові двійники через unittest.mock або власні реалізації.
- Реальні SQL-репозиторії без ORM. Параметризовані запити; жодної конкатенації користувацьких значень у SQL.
- Один сервіс, два репозиторії з Protocol-інтерфейсами та одна зовнішня залежність. Невеликі dataclass-моделі й Enum.
- Не додавай HTTP API, UI, Docker, Testcontainers, CI/CD, авторизацію, мережеві зовнішні сервіси, фонові процеси та навмисні дефекти.
- Не генеруй навчальні unit/integration-тести, звіти, coverage чи mutation-конфігурації. Допускається лише один тест доступності БД.
- Усі пояснення, коментарі й повідомлення помилок — українською. Ідентифікатори коду — англійською.

### Модель і БД

Створи рівно три таблиці:

1. `screenings`: `id` — згенерований BIGINT PRIMARY KEY; `code` — непорожній VARCHAR(40), NOT NULL UNIQUE; `capacity` — INTEGER 1–300; `evening` — BOOLEAN NOT NULL.
2. `booking_status`: `code` — PRIMARY KEY, `title` — NOT NULL UNIQUE. Лише `CONFIRMED` («Підтверджено») та `CANCELLED` («Скасовано»).
3. `bookings`: згенерований `id`; непорожній унікальний `reference` до 40 символів; `screening_id` — FOREIGN KEY на screenings; `tickets` — INTEGER 1–8; `age` — INTEGER 0–120; `total` — BIGINT >= 0; `status` — FOREIGN KEY на booking_status. Усі поля NOT NULL.

Числові обмеження забезпеч CHECK-constraints. Видалення сеансу з бронюваннями заборони через ON DELETE RESTRICT. Додай індекс за `(screening_id, status)`.

Моделі: `Screening`, `Booking`, `BookingStatus`; заявка `BookingRequest(reference, screening_id, tickets, age, student_claimed)`.

Підготуй два послідовні SQL-файли міграцій: створення схеми та заповнення статусів. Вони застосовуються один раз до порожньої тестової БД. Не додавай бізнес-дані: сеанси та бронювання створюють тести.

### Репозиторії

`ScreeningRepository`:

- `create(code, capacity, evening) -> Screening`;
- `find_by_id(id) -> Screening | None`;
- `update(screening) -> None`;
- `delete(id) -> None`.

`BookingRepository`:

- `create(booking) -> int`: повертає згенерований id, ігнорує вхідний id, зберігає решту полів;
- `find_by_id(id) -> Booking | None`;
- `find_all() -> list[Booking]`: за зростанням id;
- `update_status(id, status) -> None`;
- `delete(id) -> None`;
- `count_confirmed_tickets(screening_id) -> int`: сума tickets для CONFIRMED цього сеансу, 0 за відсутності записів;
- `find_by_screening_and_status(screening_id, status) -> list[Booking]`: фільтр за двома умовами, описаний нижче.

Оновлення відсутнього запису спричиняє ValueError, видалення відсутнього запису нічого не змінює. Помилки constraints мають доходити до виклику як винятки psycopg, а не підмінятися порожнім результатом.

Обидва репозиторії отримують відкрите з’єднання через конструктор. Власник з’єднання закриває його. Курсори закриваються після операцій. Використовуй auto-commit; кожна операція сервісу має лише одну зміну БД. Конкурентні бронювання й рівні ізоляції не входять до моделі.

### Зовнішня залежність

`StudentRegistry.is_eligible(age: int) -> bool` — Protocol, який передається сервісу через конструктор. Реальної реалізації з I/O не створюй. Тести зможуть задати True, False або виняток. Повернення значення іншого типу має спричинити RuntimeError.

### Сервіс і правила

`CinemaBookingService` отримує два репозиторії та StudentRegistry.

`create_booking(request) -> Booking`:

1. Перевір обов’язкові поля: reference непорожній, не лише пробіли, довжина до 40; screening_id — додатне ціле; tickets — 1–8; age — 0–120; student_claimed — bool. Числові поля приймають тільки int, не bool. Некоректні значення або відсутня заявка спричиняють ValueError до викликів залежностей.
2. Прочитай сеанс. Якщо його немає — ValueError.
3. Вік до 12 років виключно не допускається на вечірній сеанс: BookingRejectedError.
4. Вільні місця дорівнюють capacity мінус сумі квитків підтверджених бронювань. Якщо їх менше за запитану кількість — BookingRejectedError. Часткового бронювання немає.
5. Ціна квитка: 10 000 копійок удень, 15 000 увечері. Для віку до 12 років знижка 50%. Від 12 років за заявленої та підтвердженої студентської пільги — 20%, інакше 0%. Студентський реєстр викликається один раз лише за заявленої пільги та віку від 12 років, після перевірки місць. False не забороняє бронювання; виняток припиняє операцію без запису.
6. Відніми від базової суми знижку, округлену донизу до копійки. Від 5 квитків включно відніми ще 2 000 копійок один раз за заявку.
7. Збережи одне бронювання CONFIRMED та поверни його зі згенерованим id. Помилка збереження не повинна виглядати як успіх.

`cancel_booking(id) -> Booking`:

- id — додатний int, не bool; некоректний або відсутній id — ValueError;
- прочитай бронювання; повторне скасування — BookingRejectedError;
- зміни тільки статус на CANCELLED та поверни оновлений об’єкт;
- StudentRegistry не викликається; сума й кількість квитків залишаються незмінними;
- скасовані квитки більше не враховуються у зайнятих місцях.

Створи `BookingRejectedError` як окремий клас винятку. Усі перевірки виконуються у визначеному порядку. Дати, конкретні місця, оплата та повернення коштів не передбачені.

### Запуск і подальше розширення

Додай мінімальну конфігурацію залежностей, `.gitignore` для кешу, віртуального середовища та секретів, `.env.example` з DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. Підключення має читати змінні середовища; якщо використовуєш `.env`, явно реалізуй його завантаження. Не зберігай справжні паролі.

В окремому короткому `SETUP.md` поясни створення віртуального середовища, встановлення залежностей, створення окремої локальної БД, застосування міграцій та запуск pytest. Зазнач, що кожен тест сам створює й очищає свої бізнес-дані; автоматично очищати всю налаштовану БД заборонено.

Не прив’язуй репозиторії до конкретного порту або адреси. Ті самі міграції й параметри підключення повинні дозволяти згодом використати тимчасову PostgreSQL без зміни бізнес-коду. Інструменти наступних робіт наперед не додавай.

Перевір синтаксис та імпорт. Якщо окрема тестова БД уже явно надана студентом, перевір підключення й застосування міграцій у порожній тестовій схемі. Не використовуй сторонні БД і не приховуй відсутність середовища: повідом, що саме перевірено та що студент має налаштувати. Не встановлюй системну СУБД автоматично.

### Custom query

Реалізуй цей метод одразу під час створення SUT:

Додай до BookingRepository метод find_by_screening_and_status(screening_id, status), який повертає всі бронювання з одночасним збігом screening_id та status, за зростанням id. За відсутності збігів — порожній список. screening_id має бути додатним int, не bool; status — BookingStatus. Некоректні аргументи спричиняють ValueError до виконання SQL. Використовуй параметризований SQL і наявне перетворення рядків на Booking. Не змінюй схему та не генеруй тести.

Очікування для власних тестів визначайте за цією специфікацією. Потрібні записи, що відповідають обом умовам, лише одній або жодній; перевіряйте точний склад результатів. Помилку згенерованого коду виправляють у реалізації, а не зміною вимог.
