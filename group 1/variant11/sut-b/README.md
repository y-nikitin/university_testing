# SUT B — Оплата підписки

Це специфікація окремого мініпроєкту на JavaScript. Передайте AI-агенту: **«Виконай промпт із цього README у папці sut-b»**. Після створення перевірте запуск і зафіксуйте початкову версію в Git. Власні тести пишіть окремо; цей README залиште джерелом очікуваної поведінки. Правила й дефекти SUT A сюди автоматично не переносяться.

## Промпт для AI-агента

Створи працездатний невеликий SUT за цією специфікацією. Працюй лише в поточній `sut-b`; не змінюй `sut-a`, інші варіанти та цей README. Якщо код уже існує, перевір його й доповни без втрати роботи студента. Custom query реалізуй одразу.

### Стек і межі

Node.js 22+, JavaScript, PostgreSQL 17, pg, Jest. Один формат модулів CommonJS. Моделі — невеликі класи; статуси — незмінний набір констант; залежності — об’єкти з визначеними методами. Методи й поля — camelCase. Усі операції БД — async, усі виклики очікуються через await.

Рівно один основний сервіс, два репозиторії з реальним SQL-доступом, одна зовнішня залежність. Без ORM. Додай лише необхідні моделі, інтерфейси, конфігурацію та допоміжний код доступу до БД. SQL-поля — snake_case; назви API нижче описують контракт, адаптуй їх до стилю обраної мови.

Не додавай REST API, UI, Docker, Testcontainers, CI/CD, авторизацію, реальні зовнішні інтеграції чи навмисні дефекти. Не генеруй навчальні тести, coverage, mutation-конфігурації та звіти. Дозволено тільки один тест доступності БД. Коментарі, інструкції й повідомлення помилок — українською.

### Моделі, таблиці та міграції

Моделі: `SubscriptionAccount`, `Renewal`, `OperationStatus` зі значеннями CONFIRMED та CANCELLED; заявка `RenewalRequest(reference, account_id, users, months, nonprofit_claimed, auto_renew)`.

Створи рівно три таблиці:

1. `subscription_accounts`: згенерований BIGINT `id` PRIMARY KEY; `code` VARCHAR(40) NOT NULL UNIQUE, не порожній і не лише пробіли; monthly_price BIGINT 100–1000000; blocked BOOLEAN; overdue BOOLEAN.
2. `operation_status`: `code` PRIMARY KEY; `title` NOT NULL UNIQUE. Два записи: CONFIRMED («Підтверджено»), CANCELLED («Скасовано»).
3. `renewals`: згенерований BIGINT `id` PRIMARY KEY; непорожній унікальний `reference` VARCHAR(40); `account_id` BIGINT FOREIGN KEY на `subscription_accounts`; users INTEGER 1–50; months INTEGER 1–12; nonprofit_claimed BOOLEAN; auto_renew BOOLEAN; restoration_fee BIGINT, одне з 0 або 5000; total BIGINT >= 0; `status` FOREIGN KEY на operation_status.

Усі поля NOT NULL. Забезпеч зазначені числові межі та множини через CHECK; зовнішні ключі — ON DELETE RESTRICT. Додай індекс `(account_id, status)`. Один ресурс має багато операцій. Його не можна видалити, поки існують пов’язані записи, включно зі скасованими.

Підготуй два SQL-файли: V1 — створення таблиць і constraints, V2 — два довідникові статуси. Одноразове застосування до порожньої тестової БД. Бізнес-дані не seed-ити: їх створюють тести.

### Репозиторії

`SubscriptionAccountRepository`: create(code та всі поля ресурсу) повертає збережений ресурс; findById(id); update(resource); delete(id).

`RenewalRepository`: create(operation) повертає новий id та ігнорує переданий id; findById(id); findAll(); updateStatus(id, status); delete(id); findByResourceAndStatus(account_id, status). Зберігай усі поля переданої операції, включно зі статусом.

Відсутній запис повертається як null/None відповідно до мови. Списки сортуються за id. Оновлення відсутнього запису — помилка аргументу; видалення відсутнього запису нічого не змінює. Якщо бізнес-правила потребують сум або кількості підтверджених операцій, додай один допоміжний агрегатний метод цього репозиторію за ресурсом; він повертає 0 за відсутності записів.

Репозиторії отримують відкрите з’єднання через конструктор. Курсори/команди закривай після операцій; з’єднання закриває його власник. Використовуй параметризований SQL. Не приховуй порушення constraints. За замовчуванням — auto-commit, одна зміна БД на операцію сервісу. Конкурентні запити та блокування не моделюються.

### Сервіс та зовнішня залежність

`SubscriptionService` отримує обидва репозиторії та `NonprofitRegistry` через конструктор. Зовнішній метод `isEligible` має повертати логічне значення й приймати аргументи, зазначені в правилах нижче. Реалізації з I/O не створюй: студент передає Stub/Mock. У Python/JavaScript результат іншого типу спричиняє помилку обслуговування. Виняток залежності передається виклику без збереження операції.

`create(request)` повертає збережений `Renewal` із новим id. Спочатку, до будь-яких залежностей, перевір наявність заявки, reference (1–40 символів, не лише пробіли), додатний id ресурсу та всі типи й діапазони вхідних полів, указані в таблицях. Похідні поля обчислює сервіс. У Python числові поля — int, але не bool; у JavaScript — безпечні цілі Number, логічні — тільки boolean. У Java/C# суми та id — long. У JavaScript перетворюй BIGINT, який повертає драйвер, із перевіркою Number.isSafeInteger; небезпечні значення відхиляй.

Прочитай ресурс через реальний репозиторій; якщо його немає — помилка аргументу. Потім виконай правила у наведеному порядку:

1. Якщо blocked=true, продовження відхили до звернення до зовнішньої залежності.
2. NonprofitRegistry викликай лише за nonprofit_claimed=true, передаючи рахунок та users. false не блокує продовження.
3. База = users × months × monthly_price. Знижка: підтверджена неприбутковість та auto_renew — 25%, лише неприбутковість — 20%, лише auto_renew — 5%, інакше 0%.
4. Рівно за 12 місяців після знижки відніми 10000 копійок, але не нижче 0.
5. Рахунок вважається простроченим, якщо overdue=true і немає жодного CONFIRMED-продовження для цього рахунку. Тоді restoration_fee=5000, інакше 0. Додай внесок після знижок.
6. Операція створює лише запис продовження, не змінюючи рахунок. Скасування змінює статус; якщо скасовано всі продовження початково простроченого рахунку, наступне знову містить внесок. Календар та фактичне списання коштів не моделюються.

Усі суми — цілі копійки. Сума відсоткової знижки округлюється донизу й віднімається від бази; не округлюй кінцеву ціну замість знижки. Збережи всі поля заявки, що входять до таблиці, та похідні значення; статус успіху — CONFIRMED. Помилка запису не повинна виглядати як успіх. Відмова не створює часткових даних.

`cancel(id)` повертає оновлений об’єкт: перевір додатний цілий id, прочитай запис, відхили відсутній; якщо CANCELLED — бізнес-відмова. Виконай додаткову перевірку скасування, якщо вона задана вище. Зміни тільки статус на CANCELLED; не видаляй запис і не перераховуй збережені суми. Зовнішню залежність не викликай. Зміна ціни чи параметрів ресурсу не змінює поля попередніх операцій.

Некоректні аргументи та відсутній запис — TypeError або RangeError; бізнес-відмова — окремий клас OperationRejectedError; помилки БД — винятки pg. Для інших помилок залежностей зберігай початковий виняток.

### Custom query

Одразу реалізуй `findByResourceAndStatus(account_id, status)`: обидві умови мають одночасно збігатися. Повертай усі записи за зростанням id; якщо збігів немає — порожній список. Id — додатне ціле, status — допустиме значення OperationStatus. Некоректні аргументи відхиляй до SQL. Використовуй спільне перетворення рядків на модель.

Майбутні тести мають відрізняти записи, що відповідають обом умовам, тільки одній або жодній. Не генеруй ці тести й не підлаштовуй специфікацію під реалізацію.

### Конфігурація та перевірка

Додай мінімальні залежності й стандартну структуру проєкту. Конфігурація: .env.example з DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD; реалізуй читання середовища. Якщо підтримуєш .env, додай його завантаження та ігнорування у Git. Команди: npm install, npm test.

Додай `.gitignore` для збірок, кешів, локальних секретів і середовища. В окремому короткому SETUP.md поясни встановлення залежностей, створення окремої локальної test database, застосування міграцій, налаштування підключення та запуск. Не зберігай справжні паролі. У прикладах використовуй окрему БД `variant11_test`.

Наявний тест перевіряє лише підключення. Автоматично очищати всю налаштовану БД заборонено. Студентські тести самостійно створюватимуть і очищатимуть власні дані: спочатку операції, потім ресурси; довідник не очищується. Альтернатива — окрема схема на тест із застосуванням тих самих міграцій. Повторний запуск не повинен залежати від попереднього стану.

Адреса, порт і credentials мають передаватися конфігурацією, щоб пізніше можна було використати тимчасову PostgreSQL без зміни бізнес-коду. Не додавай інструменти наступних робіт наперед.

Перевір компіляцію або синтаксис та імпорт. Якщо студент явно надав окрему тестову БД, перевір підключення й міграції в порожній тестовій схемі. Не використовуй сторонні БД, не встановлюй системну СУБД автоматично. Чесно повідом, що перевірено та чого бракує для запуску.
