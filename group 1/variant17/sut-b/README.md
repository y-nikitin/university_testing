# SUT B — Розрахунок вартості паркування

Це специфікація окремого мініпроєкту на Java. Передайте AI-агенту: **«Виконай промпт із цього README у папці sut-b»**. Після створення перевірте запуск і зафіксуйте початкову версію в Git. Власні тести пишіть окремо; цей README залиште джерелом очікуваної поведінки. Правила й дефекти SUT A сюди автоматично не переносяться.

## Промпт для AI-агента

Створи працездатний невеликий SUT за цією специфікацією. Працюй лише в поточній `sut-b`; не змінюй `sut-a`, інші варіанти та цей README. Якщо код уже існує, перевір його й доповни без втрати роботи студента. Custom query реалізуй одразу.

### Стек і межі

Java 21+, Maven, PostgreSQL 17, JDBC, JUnit 5, Mockito. Моделі — records та enum; залежності — interfaces. Методи й поля коду — camelCase.

Рівно один основний сервіс, два репозиторії з реальним SQL-доступом, одна зовнішня залежність. Без ORM. Додай лише необхідні моделі, інтерфейси, конфігурацію та допоміжний код доступу до БД. SQL-поля — snake_case; назви API нижче описують контракт, адаптуй їх до стилю обраної мови.

Не додавай REST API, UI, Docker, Testcontainers, CI/CD, авторизацію, реальні зовнішні інтеграції чи навмисні дефекти. Не генеруй навчальні тести, coverage, mutation-конфігурації та звіти. Дозволено тільки один тест доступності БД. Коментарі, інструкції й повідомлення помилок — українською.

### Моделі, таблиці та міграції

Моделі: `ParkingZone`, `ParkingReceipt`, `OperationStatus` зі значеннями CONFIRMED та CANCELLED; заявка `ParkingReceiptRequest(reference, zone_id, minutes, entry_hour, electric, subscription_claimed)`.

Створи рівно три таблиці:

1. `parking_zones`: згенерований BIGINT `id` PRIMARY KEY; `code` VARCHAR(40) NOT NULL UNIQUE, не порожній і не лише пробіли; hourly_rate BIGINT 100–100000; daily_cap BIGINT 100–1000000; accepting BOOLEAN.
2. `operation_status`: `code` PRIMARY KEY; `title` NOT NULL UNIQUE. Два записи: CONFIRMED («Підтверджено»), CANCELLED («Скасовано»).
3. `parking_receipts`: згенерований BIGINT `id` PRIMARY KEY; непорожній унікальний `reference` VARCHAR(40); `zone_id` BIGINT FOREIGN KEY на `parking_zones`; minutes INTEGER 1–1440; entry_hour INTEGER 0–23; electric BOOLEAN; subscription_claimed BOOLEAN; billable_hours INTEGER 0–24; total BIGINT >= 0; `status` FOREIGN KEY на operation_status.

Усі поля NOT NULL. Забезпеч зазначені числові межі та множини через CHECK; зовнішні ключі — ON DELETE RESTRICT. Додай індекс `(zone_id, status)`. Один ресурс має багато операцій. Його не можна видалити, поки існують пов’язані записи, включно зі скасованими.

Підготуй два SQL-файли: V1 — створення таблиць і constraints, V2 — два довідникові статуси. Одноразове застосування до порожньої тестової БД. Бізнес-дані не seed-ити: їх створюють тести.

### Репозиторії

`ParkingZoneRepository`: create(code та всі поля ресурсу) повертає збережений ресурс; findById(id); update(resource); delete(id).

`ParkingReceiptRepository`: create(operation) повертає новий id та ігнорує переданий id; findById(id); findAll(); updateStatus(id, status); delete(id); findByResourceAndStatus(zone_id, status). Зберігай усі поля переданої операції, включно зі статусом.

Відсутній запис повертається як null/None відповідно до мови. Списки сортуються за id. Оновлення відсутнього запису — помилка аргументу; видалення відсутнього запису нічого не змінює. Якщо бізнес-правила потребують сум або кількості підтверджених операцій, додай один допоміжний агрегатний метод цього репозиторію за ресурсом; він повертає 0 за відсутності записів.

Репозиторії отримують відкрите з’єднання через конструктор. Курсори/команди закривай після операцій; з’єднання закриває його власник. Використовуй параметризований SQL. Не приховуй порушення constraints. За замовчуванням — auto-commit, одна зміна БД на операцію сервісу. Конкурентні запити та блокування не моделюються.

### Сервіс та зовнішня залежність

`ParkingService` отримує обидва репозиторії та `SubscriptionRegistry` через конструктор. Зовнішній метод `isValid` має повертати логічне значення й приймати аргументи, зазначені в правилах нижче. Реалізації з I/O не створюй: студент передає Stub/Mock. У Python/JavaScript результат іншого типу спричиняє помилку обслуговування. Виняток залежності передається виклику без збереження операції.

`create(request)` повертає збережений `ParkingReceipt` із новим id. Спочатку, до будь-яких залежностей, перевір наявність заявки, reference (1–40 символів, не лише пробіли), додатний id ресурсу та всі типи й діапазони вхідних полів, указані в таблицях. Похідні поля обчислює сервіс. У Python числові поля — int, але не bool; у JavaScript — безпечні цілі Number, логічні — тільки boolean. У Java/C# суми та id — long. У JavaScript перетворюй BIGINT, який повертає драйвер, із перевіркою Number.isSafeInteger; небезпечні значення відхиляй.

Прочитай ресурс через реальний репозиторій; якщо його немає — помилка аргументу. Потім виконай правила у наведеному порядку:

1. Якщо accepting=false, оформлення відхили.
2. До 15 хвилин включно плата і billable_hours дорівнюють 0; збережи квитанцію без виклику SubscriptionRegistry.
3. Інакше billable_hours = ceil((minutes − 15) / 60). База = min(billable_hours × hourly_rate, daily_cap).
4. SubscriptionRegistry викликай тільки за subscription_claimed=true, передаючи зону та minutes. false не блокує розрахунок.
5. Знижка: electric і чинний абонемент — 40%, лише абонемент — 30%, лише electric — 10%, інакше 0%.
6. За entry_hour >= 22 або <= 5 після знижки відніми 1000 копійок, не нижче 0. Скасування анулює квитанцію, не видаляючи її. Автомобілі, календар та фактична оплата не моделюються.

Усі суми — цілі копійки. Сума відсоткової знижки округлюється донизу й віднімається від бази; не округлюй кінцеву ціну замість знижки. Збережи всі поля заявки, що входять до таблиці, та похідні значення; статус успіху — CONFIRMED. Помилка запису не повинна виглядати як успіх. Відмова не створює часткових даних.

`cancel(id)` повертає оновлений об’єкт: перевір додатний цілий id, прочитай запис, відхили відсутній; якщо CANCELLED — бізнес-відмова. Виконай додаткову перевірку скасування, якщо вона задана вище. Зміни тільки статус на CANCELLED; не видаляй запис і не перераховуй збережені суми. Зовнішню залежність не викликай. Зміна ціни чи параметрів ресурсу не змінює поля попередніх операцій.

Некоректні аргументи та відсутній запис — IllegalArgumentException; бізнес-відмова — окремий клас OperationRejectedException; помилки БД — SQLException. Для інших помилок залежностей зберігай початковий виняток.

### Custom query

Одразу реалізуй `findByResourceAndStatus(zone_id, status)`: обидві умови мають одночасно збігатися. Повертай усі записи за зростанням id; якщо збігів немає — порожній список. Id — додатне ціле, status — допустиме значення OperationStatus. Некоректні аргументи відхиляй до SQL. Використовуй спільне перетворення рядків на модель.

Майбутні тести мають відрізняти записи, що відповідають обом умовам, тільки одній або жодній. Не генеруй ці тести й не підлаштовуй специфікацію під реалізацію.

### Конфігурація та перевірка

Додай мінімальні залежності й стандартну структуру проєкту. Конфігурація: database-test.properties без пароля; змінні DB_URL, DB_USER, DB_PASSWORD мають пріоритет. Команди: mvn -DskipTests package, mvn test.

Додай `.gitignore` для збірок, кешів, локальних секретів і середовища. В окремому короткому SETUP.md поясни встановлення залежностей, створення окремої локальної test database, застосування міграцій, налаштування підключення та запуск. Не зберігай справжні паролі. У прикладах використовуй окрему БД `variant17_test`.

Наявний тест перевіряє лише підключення. Автоматично очищати всю налаштовану БД заборонено. Студентські тести самостійно створюватимуть і очищатимуть власні дані: спочатку операції, потім ресурси; довідник не очищується. Альтернатива — окрема схема на тест із застосуванням тих самих міграцій. Повторний запуск не повинен залежати від попереднього стану.

Адреса, порт і credentials мають передаватися конфігурацією, щоб пізніше можна було використати тимчасову PostgreSQL без зміни бізнес-коду. Не додавай інструменти наступних робіт наперед.

Перевір компіляцію або синтаксис та імпорт. Якщо студент явно надав окрему тестову БД, перевір підключення й міграції в порожній тестовій схемі. Не використовуй сторонні БД, не встановлюй системну СУБД автоматично. Чесно повідом, що перевірено та чого бракує для запуску.
