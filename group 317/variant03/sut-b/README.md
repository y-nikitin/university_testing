# SUT B — Бронювання готелю, варіант 03

Python 3.12+, PostgreSQL 17, psycopg та pytest.

## Поведінка

Номер має унікальний непорожній код до 40 символів, ціну 100–1 000 000 копійок за ніч і місткість 1–6 гостей. Бронювання містить один номер на 1–30 ночей включно для 1–6 гостей, не більше місткості номера. Код бронювання унікальний, непорожній, до 40 символів. Ідентифікатори заявок — додатні цілі до 2⁶³−1; bool не допускається замість чисел. regular — лише bool.

check_in та check_out — datetime.date (не datetime). Ночі рахуються як різниця дат. Період включає дату заселення й не включає дату виїзду: виїзд попереднього гостя та заселення наступного в один день дозволені. Перетин із CONFIRMED означає зайнятість; CANCELLED не блокує номер. Поточний час не використовується, історичні дати допустимі.

Оформлення перевіряє заявку, номер, місткість і доступність, після чого один раз викликає BookingPolicy.is_allowed(room, guests, nights). False означає BookingRejectedError, відповідь іншого типу — ValueError. Виняток залежності передається виклику. За цих відмов бронювання не записується.

Успіх атомарно створює CONFIRMED і позицію зі знімком ціни. Сума — ціна × ночі мінус передбачена знижка. total, prepaid і regular фіксуються при оформленні; подальші зміни номера не змінюють розрахунків бронювання. prepaid — облік належної передоплати, яка в навчальній моделі вважається внесеною; реальної оплати немає.

Скасування змінює CONFIRMED на CANCELLED і зберігає refund, не змінюючи total та prepaid. Повторне скасування заборонене. Зовнішня залежність не викликається. days_before — передана кількість днів до заселення, ціле число 0–36500; 0 — день заселення. Вона не звіряється з поточним календарем; скасування після заселення не моделюється.

## Персональне правило

При скасуванні від 7 днів до заселення повертається 100% передоплати; за 2–6 днів — 50%; за 0–1 день — 0%. Знижок немає; передоплата дорівнює всій сумі проживання.

Усі пороги включні. Гроші — цілі копійки. Сума знижки, передоплати або повернення округлюється донизу один раз після розрахунку. Ознаки, не згадані в правилі, на розрахунок не впливають.

## API

`BookingService(rooms, bookings, policy)`:

- `calculate_total(nightly_rate, nights)` — сума проживання;
- `calculate_prepayment(total, regular=False)` — належна передоплата;
- `calculate_refund(prepaid, days_before)` — сума повернення;
- `book(BookingRequest(reference, room_id, check_in, check_out, guests, regular=False))` — оформлення;
- `cancel_booking(booking_id, days_before)` — скасування.

Окремі грошові аргументи total і prepaid мають бути цілими в межах 0–30 000 000 копійок. Некоректні входи й відсутні записи — ValueError; бізнес-відмови — BookingRejectedError. Помилки БД передаються виклику.

PostgresRoomRepository: create(Room), find_by_id, update(Room), delete. PostgresBookingRepository: create(Booking), find_by_id, is_available(room_id, check_in, check_out), find_bookings(room_id, status), cancel(booking_id, refund), delete. Контракти залежностей для тестових двійників — у hotel/ports.py.

create повертає модель з ідентифікаторами БД, ігноруючи вхідні id. find_by_id повертає None за відсутності запису. find_bookings застосовує обидві умови одночасно, впорядковує за id. is_available перевіряє лише відсутність конфлікту; існування номера перевіряє сервіс. update відсутнього номера — ValueError; cancel відсутнього чи скасованого бронювання — BookingRejectedError. Видалення відсутнього запису нічого не змінює. Видалення бронювання каскадно видаляє позицію; номер із позиціями видалити не можна.

Репозиторії отримують відкрите з’єднання від hotel.database.connect з autocommit=True. Власник закриває його через with. create використовує власну транзакцію; не обгортайте його в зовнішню транзакцію. Паралельне бронювання не підтримується: перевірка доступності та запис не захищені від конкурентних запитів. Передавайте BookingPolicy як Stub/Mock або використовуйте готовий HTTP-адаптер, описаний нижче.

## HTTP-адаптер зовнішнього дозволу

Готовий `hotel.http_booking_policy.HttpBookingPolicy` реалізує контракт BookingPolicy через HTTP. Використовує стандартну бібліотеку Python, додаткових залежностей немає. Адреса й таймаут передаються ззовні:

```python
from hotel.http_booking_policy import HttpBookingPolicy
from hotel.service import BookingService

policy = HttpBookingPolicy(base_url=wiremock_url, timeout=2)
service = BookingService(rooms, bookings, policy)
```

`wiremock_url` — базова адреса запущеного сервера, отримана студентом із контейнера: схема http/https, host і фактичний опублікований порт. Шлях, параметри та облікові дані в URL не допускаються. timeout — додатне скінченне число секунд, обмежує очікування мережевих операцій; це не загальний ліміт тривалості бізнес-сценарію.

Під час book після локальних перевірок адаптер надсилає один запит:

```http
POST /booking-policy
Content-Type: application/json
```

```json
{"roomId": 1, "guests": 2, "nights": 7}
```

roomId береться зі знайденого номера, guests — із заявки, nights — різниця дат виїзду й заселення. WireMock має повернути HTTP 200 та JSON-об’єкт із полем allowed:

```json
{"allowed": true}
```

- true дозволяє сервісу продовжити розрахунок і запис бронювання;
- false спричиняє BookingRejectedError у сервісі, без запису;
- HTTP-статус, відмінний від 200, мережева помилка, таймаут, некоректний JSON, відсутнє або нелогічне allowed спричиняють BookingPolicyError, без запису;
- значення "true", 1 і null не є логічним дозволом. Додаткові поля відповіді ігноруються;
- автоматичних повторів і переходів за HTTP-перенаправленнями немає; з’єднання закривається після виклику;
- при локальній відмові та cancel_booking HTTP-запиту немає.

Адаптер не запускає WireMock і не налаштовує його відповіді. Запуск PostgreSQL та WireMock через Testcontainers, отримання адрес, застосування міграцій, HTTP-налаштування, перевірка журналу запитів та очищення між тестами — робота студента. Сервіс також можна використовувати зі звичайним Stub/Mock замість адаптера.

## REST API

Після підготовки локальної тестової PostgreSQL та застосування міграції встановіть залежності й запустіть API з папки `sut-b`:

```sh
python -m pip install -e ".[test]"
python -m uvicorn hotel.api:app --host 127.0.0.1 --port 8080
```

Адреса — `http://127.0.0.1:8080`; документація маршрутів — `/docs`. Зупинка — Ctrl+C. Параметри БД беруться з наявних DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. Файл .env автоматично не читається. Міграції при запуску API не виконуються.

Без BOOKING_POLICY_URL використовується локальний позитивний зовнішній дозвіл. Для WireMock задайте цю змінну базовою HTTP-адресою контейнера. Перевірки місткості, зайнятості та персональні правила виконуються в обох режимах. Авторизації немає.

| Метод і шлях | Результат |
|---|---|
| `POST /rooms` | Створення номера, `201` і Location |
| `GET /rooms/{id}` | Номер, `200`; відсутній — `404` |
| `POST /bookings` | Бронювання, `201` і Location |
| `GET /bookings/{id}` | Бронювання, `200`; відсутнє — `404` |
| `POST /bookings/{id}/cancel` | Скасування та повернення, `200`; повторне — `409` |

Створення номера:

```json
{"code":"API-101","nightly_rate":10000,"capacity":2}
```

Візьміть id із відповіді й передайте як room_id:

```json
{"reference":"API-B1","room_id":1,"check_in":"2027-06-01","check_out":"2027-06-08","guests":2,"regular":false}
```

Дати передаються як YYYY-MM-DD. Відповідь бронювання містить id, reference, check_in, check_out, guests, regular, total, prepaid, refund, status та item із id, room_id, nightly_rate. Гроші — копійки; суми визначає персональне правило варіанта. Статус після створення — CONFIRMED.

Скасування потребує JSON із кількістю днів до заселення:

```json
{"days_before":5}
```

Відповідь містить CANCELLED і розрахований refund; total та prepaid зберігаються. days_before задається явно, поточна дата не використовується.

Помилки мають поля code і message: відсутній ресурс — `404 / NOT_FOUND`; бізнес-відмова — `409 / BOOKING_CONFLICT`; дубль коду — `409 / DUPLICATE_RESOURCE`; некоректні дані — `400 / INVALID_REQUEST`; збій HTTP-політики — `502 / POLICY_UNAVAILABLE`; збій БД — `500 / DATABASE_ERROR`.

На кожен запит відкривається окреме з’єднання, яке закривається після завершення; сервіс і репозиторії отримують його через Depends. Створення бронювання та позиції зберігає наявну транзакцію. Перевірка зайнятості не захищена від конкурентних бронювань: навчальні сценарії виконуйте послідовно.

API не очищає дані після зупинки. Кожен незалежний тест готує власний номер і унікальний reference через HTTP. Перевіряйте результат наступним GET. Готові API-тести до проєкту не додаються; попередні тести сервісів і репозиторіїв можна запускати як раніше.
