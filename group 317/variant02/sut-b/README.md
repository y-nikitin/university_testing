## Промпт для AI-агента

Створи в цій папці невеликий працездатний SUT на Python для оформлення замовлень інтернет-магазину. Працюй тільки в поточній папці `sut-b`; не змінюй сусідній `sut-a` та інші варіанти. Якщо файли вже існують, спочатку перевір їх і доповни наявну реалізацію без втрати роботи студента.

### Стек і межі

- Python 3.12+, PostgreSQL 17, psycopg 3, pytest; тестові двійники через unittest.mock або власні реалізації.
- Реальні SQL-репозиторії без ORM. Параметризовані запити; жодної конкатенації користувацьких значень у SQL.
- Один сервіс, два репозиторії з Protocol-інтерфейсами та одна зовнішня залежність. Невеликі dataclass-моделі й Enum.
- Не додавай HTTP API, UI, Docker, Testcontainers, CI/CD, авторизацію, мережеві зовнішні сервіси, фонові процеси та навмисні дефекти.
- Не генеруй навчальні unit/integration-тести, звіти, coverage чи mutation-конфігурації. Допускається лише один тест доступності БД.
- Усі пояснення, коментарі й повідомлення помилок — українською. Ідентифікатори коду — англійською.

### Модель і БД

Створи рівно три таблиці:

1. `products`: згенерований BIGINT `id` PRIMARY KEY; непорожній `sku` VARCHAR(40) NOT NULL UNIQUE; `unit_price` BIGINT 100–100 000 копійок; `stock` INTEGER >= 0.
2. `order_status`: `code` PRIMARY KEY, `title` NOT NULL UNIQUE. Значення CONFIRMED («Оформлено») та CANCELLED («Скасовано»).
3. `orders`: згенерований `id`; непорожній унікальний `reference` VARCHAR(40); `product_id` FOREIGN KEY на products; `quantity` INTEGER 1–20; `discount_percent` INTEGER зі значень 0, 5, 10, 20; `goods` BIGINT >= 0; `delivery` BIGINT зі значень 0, 5000; `total` BIGINT, що дорівнює goods + delivery; `status` FOREIGN KEY на order_status. Усі поля NOT NULL.

Числові правила забезпеч CHECK-constraints. Зовнішні ключі — ON DELETE RESTRICT. Додай індекс `(product_id, status)`. Один товар має багато замовлень; видалення товару із замовленнями заборонено.

Моделі: `Product`, `Order`, `OrderStatus`; заявка `OrderRequest(reference, product_id, quantity, premium, coupon_claimed)`.

Два SQL-файли міграцій: створення таблиць та заповнення двох статусів. Одноразове застосування до порожньої тестової БД. Товари й замовлення не додавай: їх створюють тести.

### Репозиторії

`ProductRepository`:

- `create(sku, unit_price, stock) -> Product`;
- `find_by_id(id) -> Product | None`;
- `update(product) -> None`;
- `delete(id) -> None`.

`OrderRepository`:

- `create(order) -> int`: повертає згенерований id, ігнорує вхідний id, зберігає решту полів;
- `find_by_id(id) -> Order | None`;
- `find_all() -> list[Order]`: за зростанням id;
- `update_status(id, status) -> None`;
- `delete(id) -> None`;
- `find_by_product_and_status(product_id, status) -> list[Order]`.

Оновлення відсутнього запису спричиняє ValueError; видалення відсутнього запису нічого не змінює. Помилки constraints передаються як винятки psycopg. Обидва репозиторії отримують відкрите з’єднання через конструктор; закриває його власник. Курсори закривай після операцій. Використовуй auto-commit: кожна операція сервісу виконує один запис у БД.

### Зовнішня залежність

`CouponValidator.is_valid(product: Product, quantity: int) -> bool` — Protocol, який передається сервісу через конструктор. Реального I/O немає. Тести задаватимуть True, False або виняток. Результат іншого типу — RuntimeError.

### Сервіс і правила

`OrderService` отримує два репозиторії та CouponValidator.

`create_order(request) -> Order`:

1. До викликів залежностей перевір заявку: reference обов’язковий, не порожній і не лише пробіли, до 40 символів; product_id — додатний int; quantity — int 1–20; premium та coupon_claimed — bool. bool не є допустимим числовим входом. Некоректний вхід або відсутня заявка — ValueError.
2. Прочитай товар. Якщо його немає — ValueError.
3. Якщо stock менший за quantity — OrderRejectedError. Часткового виконання немає.
4. Лише за coupon_claimed=True один раз виклич CouponValidator з товаром та кількістю. False не блокує замовлення, але не дає купонної знижки. Виняток передається виклику, замовлення не створюється.
5. Знижка: premium та чинний купон — 20%; лише premium — 10%; лише чинний купон — 5%; інакше 0%. Застосовуй один відсоток.
6. Базова сума — quantity × unit_price. Відніми знижку, округлену донизу до копійки. Це goods.
7. За goods >= 50 000 доставка дорівнює 0, інакше 5 000 копійок. total = goods + delivery.
8. Збережи один запис CONFIRMED із розрахованими значеннями, поверни Order зі згенерованим id. Помилку збереження не приховуй.

`cancel_order(id) -> Order`:

- id — додатний int, не bool; некоректний id або відсутнє замовлення — ValueError;
- повторне скасування — OrderRejectedError;
- зміни тільки статус на CANCELLED і поверни оновлений об’єкт;
- суми, кількість та відсоток знижки не змінюються; CouponValidator не викликається.

Створи окремий клас OrderRejectedError. Дотримуйся порядку перевірок. Залишок є вхідною умовою: оформлення й скасування його не змінюють. Резервування, відвантаження, оплата та конкурентні запити не входять у систему. Зміна ціни товару не перераховує вже збережені замовлення.

### Custom query

Реалізуй `find_by_product_and_status` одразу разом із SUT. Обидві умови обов’язкові: product_id та status мають одночасно збігатися. Поверни всі збіги за зростанням id або порожній список. product_id — додатний int, не bool; status — OrderStatus. Некоректні аргументи спричиняють ValueError до виконання SQL. Використовуй параметризований запит та спільне перетворення рядків на Order.

### Запуск і подальше розширення

Додай мінімальну конфігурацію залежностей, `.gitignore` для кешу, віртуального середовища та секретів, `.env.example` з DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. Підключення має читати змінні середовища; якщо використовуєш `.env`, явно реалізуй його завантаження. Не зберігай справжні паролі.

В окремому короткому `SETUP.md` поясни створення віртуального середовища, встановлення залежностей, створення окремої локальної БД, застосування міграцій та запуск pytest. Зазнач, що кожен тест сам створює й очищає свої бізнес-дані; автоматично очищати всю налаштовану БД заборонено.

Не прив’язуй репозиторії до конкретного порту або адреси. Ті самі міграції й параметри підключення повинні дозволяти згодом використати тимчасову PostgreSQL без зміни бізнес-коду. Інструменти наступних робіт наперед не додавай.

Перевір синтаксис та імпорт. Якщо окрема тестова БД уже явно надана студентом, перевір підключення й застосування міграцій у порожній тестовій схемі. Не використовуй сторонні БД і не приховуй відсутність середовища: повідом, що саме перевірено та що студент має налаштувати. Не встановлюй системну СУБД автоматично.
