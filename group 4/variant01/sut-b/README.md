# SUT B — Інтернет-магазин, варіант 01

JavaScript, Node.js 22+, PostgreSQL 17, pg, Jest. SUT A залишається окремою системою.

## Персональні правила

До 5 одиниць включно. Знижка 17% від 1000 грн включно незалежно від преміальності. Повернення до 3 днів включно лише із закритим пакуванням; акційність не обмежує повернення.

Пороги рахуються від суми до знижки. Гроші — цілі копійки; сума знижки округлюється донизу. Доставки та інших доплат немає.

## Склад і поведінка

Моделі Product, Order та OrderItem; замовлення містить одну позицію одного товару. Ціна 100–1 000 000 копійок, залишок невід’ємний. Кількість заявки 1–20; персональний ліміт перевіряється як бізнес-умова. Залишок перевіряється, але оформлення й повернення його не змінюють.

`OrderService(products, orders, policy)`:

- `placeOrder(new OrderRequest(reference, productId, quantity, premium))`: валідація, пошук товару, персональний ліміт, залишок, зовнішній дозвіл, розрахунок, запис CONFIRMED.
- `calculateTotal(unitPrice, quantity, premium)`: чистий розрахунок суми за персональним правилом.
- `returnOrder(id, daysSincePurchase, packagingOpen=false)`: перевіряє існування, попереднє повернення та персональні умови; змінює лише статус на RETURNED. Дні — цілі 0–36500, день покупки — 0.

Код reference — непорожній унікальний рядок до 40 символів, id — додатні безпечні цілі. Логічні поля — тільки boolean. Ціна й акційність зберігаються в позиції на момент оформлення; зміни товару не перераховують замовлення та не змінюють умови його повернення. Повторне повернення заборонене.

Зовнішня залежність `OrderPolicy.isAllowed(product, quantity)` підміняється Stub/Mock. Викликається один раз після перевірки залишку; false — OrderRejectedError, виняток припиняє оформлення без запису. При поверненні залежність не викликається. Некоректні входи — TypeError/RangeError, бізнес-відмови — OrderRejectedError; помилки БД передаються виклику.

`ProductRepository` і `OrderRepository` — реальні PostgreSQL-реалізації. Є create, findById, update/updateStatus, delete; для замовлень — findAll і findOrders(productId, status). Фільтр вимагає обох умов, списки впорядковані за id, відсутній запис — null. Видалення замовлення видаляє позицію; товар із позиціями видалити не можна. Поле couponValid у спільній моделі завжди false: купони у цьому варіанті не використовуються.

Усі методи з БД асинхронні; використовуйте await. Репозиторії отримують один виділений відкритий pg.Client. Не запускайте паралельні операції на ньому й не обгортайте create у зовнішню транзакцію: замовлення та позиція зберігаються разом у власній транзакції репозиторію. Окремого навчального завдання на rollback немає.

## Підготовка та запуск

```sh
npm install
```

У локальній PostgreSQL створіть навчального користувача (один раз) і окрему БД:

```sql
CREATE ROLE store_student LOGIN;
\password store_student
CREATE DATABASE store_variant01_test OWNER store_student;
```

Із цієї папки застосуйте міграції один раз до нової БД:

```sh
psql -h localhost -U store_student -d store_variant01_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U store_student -d store_variant01_test -v ON_ERROR_STOP=1 -f migrations/V2__add_indexes.sql
```

Таблиці порожні: статуси визначені CHECK, товари й замовлення створюють тести. Налаштуйте DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD у середовищі. `.env.example` — лише приклад, автоматичного читання .env немає. Зокрема встановіть DB_NAME=store_variant01_test.

```sh
npm test
```

Наявний тест перевіряє лише підключення. Власні тести додавайте в tests. Функція connect із src/database.js повертає відкритий клієнт; його власник викликає await client.end(). Схеми та дані автоматично не очищаються. Кожен тест видаляє власні замовлення перед товарами або використовує окрему тестову схему. Реальні платежі, календар і конкуренція не моделюються.
