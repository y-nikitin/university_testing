# SUT B — Інтернет-магазин, варіант 06

JavaScript, Node.js 22+, PostgreSQL 17, pg, Jest. SUT A залишається окремою системою.

## Персональні правила

До 6 одиниць, преміальному покупцю — до 10. Знижка 10% від 900 грн включно і лише преміальному покупцю. Повернення до 5 днів включно; акційні товари не повертаються, стан пакування на дозвіл не впливає.

Пороги рахуються від суми до знижки. Гроші — цілі копійки; сума знижки округлюється донизу. Доставки та інших доплат немає.

## Склад і поведінка

Моделі Product, Order та OrderItem; замовлення містить одну позицію одного товару. Ціна 100–1 000 000 копійок, залишок невід’ємний. Кількість заявки 1–20; персональний ліміт перевіряється як бізнес-умова. Залишок перевіряється, але оформлення й повернення його не змінюють.

`OrderService(products, orders, policy)`:

- `placeOrder(new OrderRequest(reference, productId, quantity, premium))`: валідація, пошук товару, персональний ліміт, залишок, зовнішній дозвіл, розрахунок, запис CONFIRMED.
- `calculateTotal(unitPrice, quantity, premium)`: чистий розрахунок суми за персональним правилом.
- `returnOrder(id, daysSincePurchase, packagingOpen=false)`: перевіряє існування, попереднє повернення та персональні умови; змінює лише статус на RETURNED. Дні — цілі 0–36500, день покупки — 0.

Код reference — непорожній унікальний рядок до 40 символів, id — додатні безпечні цілі. Логічні поля — тільки boolean. Ціна й акційність зберігаються в позиції на момент оформлення; зміни товару не перераховують замовлення та не змінюють умови його повернення. Повторне повернення заборонене.

Зовнішня залежність `OrderPolicy.isAllowed(product, quantity)` підміняється Stub/Mock. Викликається один раз після перевірки залишку; false — OrderRejectedError, виняток припиняє оформлення без запису. При поверненні залежність не викликається. Некоректні входи — TypeError/RangeError, бізнес-відмови — OrderRejectedError; помилки БД передаються виклику.

`ProductRepository` і `OrderRepository` — реальні PostgreSQL-реалізації. Є create, findById, update/updateStatus, delete; для замовлень — findAll і findOrders(productId, status). Фільтр вимагає обох умов, списки впорядковані за id, відсутній запис — null. Видалення замовлення видаляє позицію; товар із позиціями видалити не можна. Поле couponValid у спільній моделі завжди false: купони у цьому варіанті не використовуються.

Усі методи з БД асинхронні; використовуйте await. Репозиторії отримують один виділений відкритий pg.Client. Не запускайте паралельні операції на ньому й не обгортайте create у зовнішню транзакцію: замовлення та позиція зберігаються разом у власній транзакції репозиторію. Окремого навчального завдання на rollback немає.

## HTTP-адаптер зовнішнього дозволу

`src/http-order-policy.js` містить готовий HttpOrderPolicy, сумісний з OrderPolicy. Використовується вбудований fetch Node.js 22+, додаткових залежностей немає.

```javascript
const { HttpOrderPolicy } = require("./src/http-order-policy");
const { OrderService } = require("./src/service");

const policy = new HttpOrderPolicy(wiremockUrl, 2000);
const service = new OrderService(products, orders, policy);
```

wiremockUrl — базова HTTP(S)-адреса з host і фактичним опублікованим портом контейнера, без шляху, параметрів та облікових даних. Другий аргумент — таймаут у мілісекундах (ціле число 1–2147483647, за замовчуванням 2000), для запиту й читання відповіді.

Після локальних перевірок сервіс викликає адаптер, який надсилає один запит:

```http
POST /order-policy
Content-Type: application/json
```

```json
{"productId": 1, "quantity": 2}
```

Очікується HTTP 200 і JSON-об’єкт:

```json
{"allowed": true}
```

- true дозволяє оформлення: персональний розрахунок суми й запис CONFIRMED;
- false спричиняє OrderRejectedError у сервісі, запису немає;
- інший HTTP-статус, мережева помилка, таймаут, некоректний JSON, відсутнє або нелогічне allowed спричиняють OrderPolicyError, без запису;
- "true", 1 і null не є логічним дозволом; додаткові поля відповіді ігноруються;
- при локальній відмові та returnOrder HTTP не викликається;
- повторних запитів і переходів за HTTP-перенаправленнями немає.

Адаптер не запускає WireMock. Контейнери PostgreSQL і WireMock, адреси, міграції, налаштування відповідей, перевірки БД та журналу HTTP і очищення між тестами налаштовує студент. Звичайні Stub/Mock для OrderPolicy також підтримуються.

## Підготовка та запуск

```sh
npm install
```

У локальній PostgreSQL створіть навчального користувача (один раз) і окрему БД:

```sql
CREATE ROLE store_student LOGIN;
\password store_student
CREATE DATABASE store_variant06_test OWNER store_student;
```

Із цієї папки застосуйте міграції один раз до нової БД:

```sh
psql -h localhost -U store_student -d store_variant06_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U store_student -d store_variant06_test -v ON_ERROR_STOP=1 -f migrations/V2__add_indexes.sql
```

Таблиці порожні: статуси визначені CHECK, товари й замовлення створюють тести. Налаштуйте DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD у середовищі. `.env.example` — лише приклад, автоматичного читання .env немає. Зокрема встановіть DB_NAME=store_variant06_test.

```sh
npm test
```

Наявний тест перевіряє лише підключення. Власні тести додавайте в tests. Функція connect із src/database.js повертає відкритий клієнт; його власник викликає await client.end(). Схеми та дані автоматично не очищаються. Кожен тест видаляє власні замовлення перед товарами або використовує окрему тестову схему. Реальні платежі, календар і конкуренція не моделюються.

## REST API

Після підготовки тестової PostgreSQL та застосування наявної міграції запустіть із папки `sut-b`:

```sh
npm install
npm start
```

API працює на `http://127.0.0.1:8080`; інший порт задається через API_PORT. Зупинка — Ctrl+C. Параметри БД: DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. Файл .env автоматично не читається. Міграції автоматично не виконуються.

| Метод і шлях | Результат |
|---|---|
| `POST /products` | Створення товару, `201` і Location |
| `GET /products/{id}` | Товар, `200`; відсутній — `404` |
| `POST /orders` | Створення замовлення, `201` і Location |
| `GET /orders/{id}` | Замовлення, `200`; відсутнє — `404` |
| `POST /orders/{id}/return` | Повернення, `200`; повторне чи заборонене — `409` |

Товар:

```json
{"sku":"API-P1","unitPrice":60000,"stock":10,"onSale":false}
```

Використайте id відповіді як productId:

```json
{"reference":"API-O1","productId":1,"quantity":2,"premium":true}
```

Замовлення повертає id, reference, premium, couponValid, total, status та item із id, productId, quantity, unitPrice, onSale. Гроші — копійки; сума визначається персональним правилом цього варіанта. Початковий статус — CONFIRMED.

Тіло повернення:

```json
{"daysSincePurchase":2,"packagingOpen":false}
```

Успіх повертає RETURNED зі збереженою total. Персональні ліміти, знижки, строки й умови повернення залишаються чинними.

Без ORDER_POLICY_URL локальна зовнішня політика дозволяє оформлення. Для WireMock задайте цю змінну базовою адресою контейнера; використовується наявний контракт POST /order-policy. Авторизації немає.

Помилки містять code і message: `404 / NOT_FOUND`, `409 / ORDER_CONFLICT`, дубль коду — `409 / DUPLICATE_RESOURCE`, некоректний запит — `400 / INVALID_REQUEST`, збій HTTP-політики — `502 / POLICY_UNAVAILABLE`. Непідтримуваний метод — `405`, внутрішня помилка — `500`.

На кожну операцію відкривається окреме з’єднання PostgreSQL, яке закривається після її завершення. Транзакція замовлення з позицією збережена. Залишок лише перевіряється; не зменшується. Використовуйте послідовні навчальні сценарії.

Дані після зупинки API залишаються в БД. Кожен незалежний тест створює власний товар та унікальний reference через API; результат перевіряється GET. Готові API-тести не додаються, попередні тести сервісів і репозиторіїв збережені.
