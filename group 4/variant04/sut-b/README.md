# SUT B — Інтернет-магазин, варіант 04

Python 3.12+, PostgreSQL 17, psycopg 3, pytest. Це окрема система; правила SUT A не переносяться сюди.

## Персональні правила

- До 4 одиниць товару включно, преміальному покупцю — до 8. Універсальний діапазон кількості — 1–20; перевищення персонального ліміту є бізнес-відмовою.
- Знижка 15%, якщо сума до знижки становить від 1200 грн включно **і** купон підтверджено. Без обох умов знижки немає.
- Повернення протягом 7 днів включно; акційні товари поверненню не підлягають. День покупки — 0. Ознака відкритого пакування у цьому варіанті не впливає на дозвіл.

## Модель та API

`Product` — товар із ціною, залишком та ознакою акційності. `Order` — замовлення. `OrderItem` — його єдина позиція. Три відповідні таблиці мають PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL і CHECK. Замовлення містить рівно один вид товару.

`OrderService` отримує реальні `ProductRepository`, `OrderRepository` та зовнішній `CouponValidator`. Реалізації PostgreSQL містяться в `store/repositories.py`.

- `place_order(OrderRequest(reference, product_id, quantity, premium, coupon_claimed))`: перевіряє заявку, існування товару, персональний ліміт, залишок, потім купон; зберігає замовлення CONFIRMED із позицією та повертає його.
- `calculate_total(unit_price, quantity, coupon_valid)`: повертає підсумок у копійках. Ціна 100–1 000 000, кількість 1–20. Знижка обчислюється цілочисельно з округленням донизу. Доставки та інших доплат немає.
- `return_order(order_id, days_since_purchase, packaging_open=False)`: перевіряє аргументи, існування замовлення, відсутність попереднього повернення та персональні умови; змінює лише статус на RETURNED. Зовнішню залежність не викликає. Дні передаються цілим числом 0–36500; системний годинник не використовується.

Код замовлення — непорожній унікальний рядок до 40 символів. Id додатні. Числові входи приймають int, але не bool; логічні — тільки bool. Неправильні аргументи й відсутній запис спричиняють ValueError, бізнес-відмови — OrderRejectedError. Помилки БД і залежності не приховуються.

Купон перевіряється один раз лише за coupon_claimed=True, після перевірок товару, кількості та залишку. False не блокує оформлення. Виняток або відповідь іншого типу припиняє операцію без запису.

Ціна й акційність копіюються в позицію на момент покупки. Подальша зміна товару не впливає на попередні суми та можливість повернення. Оформлення і повернення не змінюють складський залишок. Резервування, реальні платежі та конкурентні зміни не моделюються.

Репозиторії мають створення, читання, зміну та видалення. Відсутній запис — None; оновлення відсутнього запису — ValueError, видалення — без змін. `find_orders(product_id, status)` фільтрує одночасно за товаром і статусом, повертає записи за зростанням id або порожній список. Видалення замовлення видаляє його позицію; товар із позиціями видалити не можна.

## HTTP-перевірка купона

Готовий `store.http_coupon_validator.HttpCouponValidator` реалізує контракт CouponValidator через HTTP. Використовує стандартну бібліотеку Python без додаткових залежностей.

```python
from store.http_coupon_validator import HttpCouponValidator
from store.service import OrderService

coupons = HttpCouponValidator(base_url=wiremock_url, timeout=2)
service = OrderService(products, orders, coupons)
```

wiremock_url — адреса контейнера, отримана під час його запуску: http/https, host і фактичний опублікований порт, без шляху, параметрів та облікових даних. timeout — додатне скінченне число секунд очікування мережевих операцій, не загальний ліміт бізнес-сценарію.

Лише за coupon_claimed=True, після локальних перевірок, виконується один запит:

```http
POST /coupon-validation
Content-Type: application/json
```

```json
{"productId": 1, "quantity": 2}
```

Очікується HTTP 200 і JSON-об’єкт:

```json
{"valid": true}
```

- true: у БД зберігається coupon_valid=True; від початкової суми 1200 грн включно застосовується знижка 15%. Нижче порога купон зберігається підтвердженим, але знижки немає;
- false: замовлення створюється без знижки, coupon_valid=False;
- HTTP-статус, відмінний від 200, мережева помилка, таймаут, некоректний JSON, відсутнє або нелогічне valid: CouponValidationError, без запису замовлення;
- "true", 1 і null не є логічним результатом; додаткові поля відповіді ігноруються;
- за coupon_claimed=False, при локальній відмові та return_order HTTP не викликається;
- повторів і переходів за HTTP-перенаправленнями немає; з’єднання закривається після виклику.

Адаптер не запускає WireMock. Контейнери PostgreSQL і WireMock, застосування міграцій, налаштування відповідей, перевірки БД та журналу HTTP і очищення між тестами налаштовує студент. Звичайний Stub/Mock для CouponValidator також підтримується.

## Підготовка і запуск

Із цієї папки:

```sh
python -m venv .venv
```

Активуйте середовище (`.venv\Scripts\Activate.ps1` у PowerShell або `source .venv/bin/activate` у bash), потім:

```sh
python -m pip install -e ".[test]"
```

У локальній PostgreSQL від адміністратора створіть окремі навчальні роль та БД:

```sql
CREATE ROLE store_student LOGIN;
\password store_student
CREATE DATABASE store_variant04_test OWNER store_student;
```

До нової БД один раз застосуйте міграції:

```sh
psql -h localhost -U store_student -d store_variant04_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U store_student -d store_variant04_test -v ON_ERROR_STOP=1 -f migrations/V2__add_indexes.sql
```

Seed-даних немає: статуси визначені CHECK-обмеженням, а товари та замовлення створюють тести.

Параметри підключення — змінні DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. `.env.example` є лише переліком параметрів: файли `.env` автоматично не читаються. У PowerShell пароль можна передати так:

```powershell
$secret = Read-Host 'Пароль тестової БД' -AsSecureString
$env:DB_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
python -m pytest
```

Наявний тест перевіряє тільки підключення. Власні тести додавайте в `tests/`. Через `store.database.connect()` відкрийте з’єднання, передайте його обом репозиторіям, а їх і тестовий CouponValidator — сервісу. З’єднання закриває його власник. Зовнішнього сервера застосунку немає.

Схеми та дані автоматично не очищаються. Кожен тест має підготувати й видалити свої замовлення, потім товари, або використовувати власну тестову схему. Збереження замовлення з позицією атомарне; спеціально тестувати транзакції не потрібно.

## REST API

Підготуйте локальну тестову PostgreSQL та застосуйте наявну міграцію. Із папки `sut-b`:

```sh
python -m pip install -e ".[test]"
python -m uvicorn store.api:app --host 127.0.0.1 --port 8080
```

API: `http://127.0.0.1:8080`, документація: `/docs`. Зупинка: Ctrl+C. Підключення використовує DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD з попередніх інструкцій. Файл .env автоматично не читається; міграції при запуску не виконуються.

| Метод і шлях | Результат |
|---|---|
| `POST /products` | Створення товару, `201` і Location |
| `GET /products/{id}` | Товар, `200`; відсутній — `404` |
| `POST /orders` | Створення замовлення, `201` і Location |
| `GET /orders/{id}` | Замовлення, `200`; відсутнє — `404` |
| `POST /orders/{id}/return` | Повернення, `200`; заборонене чи повторне — `409` |

Створення товару:

```json
{"sku":"API-P1","unit_price":60000,"stock":10,"on_sale":false}
```

Використайте отриманий id як product_id у замовленні:

```json
{"reference":"API-O1","product_id":1,"quantity":2,"premium":false,"coupon_claimed":true}
```

Відповідь містить id, reference, premium, coupon_valid, total, status і item із id, product_id, quantity, unit_price, on_sale. Гроші — копійки. У локальному режимі приклад дає total=102000 та CONFIRMED.

Без COUPON_VALIDATOR_URL локальний валідатор підтверджує заявлений купон. Якщо coupon_claimed=false, валідатор не викликається й знижки немає. Для перевірки через WireMock задайте COUPON_VALIDATOR_URL базовою адресою контейнера. HTTP-контракт `/coupon-validation` описано вище. Відповідь valid=false означає оформлення без знижки, а не відмову в замовленні. Авторизації немає.

Повернення потребує JSON:

```json
{"days_since_purchase":7,"packaging_open":false}
```

Успіх повертає замовлення зі статусом RETURNED; total незмінний. Після 7 днів або для акційного товару — бізнес-відмова. Персональні ліміти 4/8 одиниць і знижка 15% від 1200 грн із підтвердженим купоном залишаються чинними.

Помилки містять code і message: `404 / NOT_FOUND`, `409 / ORDER_CONFLICT`, дубль коду — `409 / DUPLICATE_RESOURCE`, некоректні дані — `400 / INVALID_REQUEST`, збій HTTP-перевірки купона — `502 / COUPON_UNAVAILABLE`, помилка БД — `500 / DATABASE_ERROR`.

З’єднання з БД відкривається для запиту й закривається після його завершення. Сервіс та репозиторії отримують його через Depends. Транзакція створення замовлення разом із позицією збережена. Залишок товару, як і раніше, лише перевіряється, а не зменшується.

API не очищає дані після зупинки. Кожен незалежний тест створює власний товар і унікальний reference через HTTP; результат перевіряється наступним GET. Готові API-тести не додаються. Попередні тести сервісів і репозиторіїв залишаються придатними до запуску.
