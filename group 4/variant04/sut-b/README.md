# SUT B — Інтернет-магазин, варіант 04

Python 3.12+, PostgreSQL 17, psycopg 3, pytest. Це окрема система; правила SUT A не переносяться сюди.

## Персональні правила

- До 4 одиниць товару включно, преміальному покупцю — до 8. Універсальний діапазон кількості — 1–20; перевищення персонального ліміту є бізнес-відмовою.
- Знижка 15%, якщо сума до знижки становить від 1200 грн включно **і** купон підтверджено. Без обох умов знижки немає.
- Повернення протягом 7 днів включно; акційні товари поверненню не підлягають. День покупки — 0. Ознака відкритого пакування у цьому варіанті не впливає на дозвіл.

## Модель та API

`Product` — товар із ціною, залишком та ознакою акційності. `Order` — замовлення. `OrderItem` — його єдина позиція. Три відповідні таблиці мають PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL і CHECK. Замовлення містить рівно один вид товару.

`OrderService` отримує реальні `ProductRepository`, `OrderRepository` та зовнішній `CouponValidator`. Реалізації PostgreSQL містяться в `store/repositories.py`.

- `place_order(OrderRequest(reference, product_id, quantity, premium, coupon_claimed))`: перевіряє заявку, існування товару, персональний ліміт, залишок, потім купон; зберігає замовлення CONFIRMED із позицією та повертає його.
- `calculate_total(unit_price, quantity, coupon_valid)`: повертає підсумок у копійках. Ціна 100–1 000 000, кількість 1–20. Знижка обчислюється цілочисельно з округленням донизу. Доставки та інших доплат немає.
- `return_order(order_id, days_since_purchase, packaging_open=False)`: перевіряє аргументи, існування замовлення, відсутність попереднього повернення та персональні умови; змінює лише статус на RETURNED. Зовнішню залежність не викликає. Дні передаються цілим числом 0–36500; системний годинник не використовується.

Код замовлення — непорожній унікальний рядок до 40 символів. Id додатні. Числові входи приймають int, але не bool; логічні — тільки bool. Неправильні аргументи й відсутній запис спричиняють ValueError, бізнес-відмови — OrderRejectedError. Помилки БД і залежності не приховуються.

Купон перевіряється один раз лише за coupon_claimed=True, після перевірок товару, кількості та залишку. False не блокує оформлення. Виняток або відповідь іншого типу припиняє операцію без запису.

Ціна й акційність копіюються в позицію на момент покупки. Подальша зміна товару не впливає на попередні суми та можливість повернення. Оформлення і повернення не змінюють складський залишок. Резервування, реальні платежі та конкурентні зміни не моделюються.

Репозиторії мають створення, читання, зміну та видалення. Відсутній запис — None; оновлення відсутнього запису — ValueError, видалення — без змін. `find_orders(product_id, status)` фільтрує одночасно за товаром і статусом, повертає записи за зростанням id або порожній список. Видалення замовлення видаляє його позицію; товар із позиціями видалити не можна.

## Підготовка і запуск

Із цієї папки:

```sh
python -m venv .venv
```

Активуйте середовище (`.venv\Scripts\Activate.ps1` у PowerShell або `source .venv/bin/activate` у bash), потім:

```sh
python -m pip install -e ".[test]"
```

У локальній PostgreSQL від адміністратора створіть окремі навчальні роль та БД:

```sql
CREATE ROLE store_student LOGIN;
\password store_student
CREATE DATABASE store_variant04_test OWNER store_student;
```

До нової БД один раз застосуйте міграції:

```sh
psql -h localhost -U store_student -d store_variant04_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U store_student -d store_variant04_test -v ON_ERROR_STOP=1 -f migrations/V2__add_indexes.sql
```

Seed-даних немає: статуси визначені CHECK-обмеженням, а товари та замовлення створюють тести.

Параметри підключення — змінні DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. `.env.example` є лише переліком параметрів: файли `.env` автоматично не читаються. У PowerShell пароль можна передати так:

```powershell
$secret = Read-Host 'Пароль тестової БД' -AsSecureString
$env:DB_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
python -m pytest
```

Наявний тест перевіряє тільки підключення. Власні тести додавайте в `tests/`. Через `store.database.connect()` відкрийте з’єднання, передайте його обом репозиторіям, а їх і тестовий CouponValidator — сервісу. З’єднання закриває його власник. Зовнішнього сервера застосунку немає.

Схеми та дані автоматично не очищаються. Кожен тест має підготувати й видалити свої замовлення, потім товари, або використовувати власну тестову схему. Збереження замовлення з позицією атомарне; спеціально тестувати транзакції не потрібно.
