# SUT B — Інтернет-магазин

Java 21, Maven, PostgreSQL 17, Spring Boot, JdbcTemplate, JUnit 5 та Mockito. Варіант 13: базовий магазин із персональним правилом знижки.

## Поведінка

- Товар має унікальний непорожній артикул до 40 символів, ціну 100–1 000 000 копійок, невід’ємний залишок та ознаку акційності.
- Замовлення містить одну позицію одного товару. Кількість — 1–20 включно; код замовлення — унікальний непорожній рядок до 40 символів. Ідентифікатор товару додатний.
- Оформлення перевіряє наявність товару та достатність залишку. Потім один раз викликає зовнішній дозвіл `OrderPolicy.isAllowed(product, quantity)`. Відмова або виняток припиняє оформлення без запису.
- Сума — ціна × кількість мінус знижка, у цілих копійках, без доплат. Преміальність і підтвердженість купона зберігаються в замовленні.
- Успішне оформлення зберігає замовлення CONFIRMED і позицію з ціною та акційністю на момент покупки. Подальші зміни товару не змінюють замовлення.
- Повернення змінює CONFIRMED на RETURNED. Повторне повернення заборонене. Обмежень за днями, пакуванням або акційністю поки немає. Зовнішній дозвіл при поверненні не викликається.
- Оформлення й повернення не змінюють залишок товару.

## Персональна функція: розрахунок знижки

5% за преміальність та 7% від 1200 грн. Відсотки додаються: разом 12%.

Усі пороги включні й визначаються за сумою до знижки. Сума знижки округлюється донизу до цілої копійки та віднімається один раз. Якщо жодна умова не виконується, знижка становить 0%. Ознаки, не згадані в правилі, на знижку не впливають. Загальний ліміт кількості 1–20 та базове повернення залишаються без змін.

`couponValid` — вхідна ознака вже підтвердженого купона; перевірка кодів купонів не входить до цієї системи. Акційність береться з товару, преміальність — із заявки.

## API

`OrderService(products, orders, policy)`:

- `calculateTotal(unitPrice, quantity, premium, couponValid, onSale)` — розрахунок суми за персональним правилом; коротка форма з двома аргументами використовує false для всіх ознак;
- `placeOrder(new OrderRequest(reference, productId, quantity, premium, couponValid))` — оформлення з персональною знижкою; конструктор без couponValid використовує false;
- `returnOrder(id)` — повернення.

Некоректні входи та відсутні товари/замовлення — `IllegalArgumentException`; бізнес-відмови — `OrderRejectedException`. Помилки БД передаються як `SQLException`.

`ProductRepository(connection)`: create, findById, update, delete.
`OrderRepository(connection)`: create, findById, findAll, findOrders(productId, status), updateStatus, delete.

create повертає збережену модель з ідентифікаторами БД; вхідні id ігноруються. findById повертає null за відсутності запису. findOrders застосовує обидві умови одночасно. Списки впорядковані за id. Оновлення відсутнього запису викликає IllegalArgumentException, видалення — нічого не змінює. Видалення замовлення каскадно видаляє позицію; товар із позиціями видалити не можна. Обмеження таблиць перевіряє PostgreSQL.

У REST-застосунку Spring керує залежностями та з’єднаннями; репозиторії працюють через JdbcTemplate. Конструктори з JDBC Connection залишені для окремих тестів: таке з’єднання закриває тест. Деталі операцій і транзакцій визначає реалізація репозиторію. Для бізнес-сценаріїв використовуйте послідовні операції та ізольовані дані.

## Запуск

Створіть навчального користувача та окрему тестову БД у локальній PostgreSQL:

```sql
CREATE ROLE store_student LOGIN;
\password store_student
CREATE DATABASE store_variant13_test OWNER store_student;
```

Із папки sut-b застосуйте міграції один раз до нової БД:

```sh
psql -h localhost -U store_student -d store_variant13_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U store_student -d store_variant13_test -v ON_ERROR_STOP=1 -f migrations/V2__add_indexes.sql
```

Налаштуйте змінні середовища за `.env.example`; файл .env автоматично не читається. Пароль задайте через DB_PASSWORD.

```sh
mvn compile
mvn test
```

Початковий тест перевіряє підключення до БД; regression suite запускається окремо. Таблиці спочатку порожні; дані для сценаріїв готуйте у власних тестах. Схеми та дані автоматично не створюються й не очищаються при запуску тестів. Для незалежності тестів очищайте власні замовлення перед товарами або використовуйте окрему тестову схему.

## REST API через Spring Boot

Підготуйте локальну тестову PostgreSQL, застосуйте наявну міграцію й задайте DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD за попередніми інструкціями. Із папки sut-b:

```sh
mvn spring-boot:run
```

Або запустіть `StoreApplication.main()` в IDE. Адреса: `http://127.0.0.1:8080`; порт задається API_PORT. Зупинка — Ctrl+C. Міграції автоматично не виконуються, файл .env автоматично не читається.

| Метод і шлях | Результат |
|---|---|
| `POST /products` | Створення товару, `201` і Location |
| `GET /products/{id}` | Товар, `200`; відсутній — `404` |
| `POST /orders` | Створення замовлення, `201` і Location |
| `GET /orders/{id}` | Замовлення, `200`; відсутнє — `404` |
| `POST /orders/{id}/return` | Повернення без тіла запиту, `200`; повторне — `409` |

Товар:

```json
{"sku":"API-P1","unitPrice":60000,"stock":10,"onSale":false}
```

Замовлення з отриманим productId:

```json
{"reference":"API-O1","productId":1,"quantity":2,"premium":true,"couponValid":true}
```

Замовлення повертає id, reference, premium, couponValid, total, status та item із id, productId, quantity, unitPrice, onSale. Гроші — копійки. Total визначає персональне правило саме цього варіанта. Повернення змінює CONFIRMED на RETURNED, сума зберігається. Дні й пакування у Java-варіантах не є параметрами повернення.

Без ORDER_POLICY_URL локальна зовнішня політика дозволяє оформлення. Для WireMock задайте цю змінну базовою адресою контейнера; використовується наявний контракт POST /order-policy. couponValid залишається вхідною ознакою підтвердженого купона. Авторизації немає.

Помилки мають code і message: `404 / NOT_FOUND`, `409 / ORDER_CONFLICT`, дубль коду — `409 / DUPLICATE_RESOURCE`, некоректні дані — `400 / INVALID_REQUEST`, збій HTTP-політики — `502 / POLICY_UNAVAILABLE`, помилка БД — `500 / DATABASE_ERROR`.

Сервіс позначено @Service, репозиторії — @Repository. Spring створює DataSource із пулом HikariCP; JdbcTemplate виконує SQL. Замовлення й позиція зберігаються однією транзакцією через TransactionTemplate. Залишок лише перевіряється, а не зменшується. Використовуйте послідовні навчальні сценарії.

Конструктори репозиторіїв із Connection залишено для попередніх тестів; передане з’єднання закриває його власник. SQL-помилки JdbcTemplate повертаються як підтипи DataAccessException, тому тести, що очікували SQLException від виконання SQL, потрібно адаптувати. Підключення Database.connect залишається доступним.

API не очищає дані після зупинки. Кожен незалежний тест створює власний товар і унікальний reference через HTTP; результат перевіряється GET. Готові API-тести не додаються.


## UI та окремий regression suite

Готовий UI розташований у сусідній папці [sut-c-ui](../sut-c-ui/README.md).
Він доступний після звичайного запуску цього backend на /index.html; окрема збірка frontend не потрібна.
Запускайте backend із папки sut-b. Порт за замовчуванням — 8080.

Regression suite — окремий навчальний набір із навмисними проблемами стабільності.
Для його запуску потрібен Docker; PostgreSQL піднімається через Testcontainers, міграції застосовуються набором.
Команда з цієї папки:

```sh
mvn -Pregression test
```

Звичайні тести та цей окремий набір мають різні умови запуску.
Студентські тести повинні перевіряти вимоги та фактичний стан системи; повторні запуски мають бути незалежними.
Для security testing використовуйте окремі vulnerable-копії, а не цей SUT.
