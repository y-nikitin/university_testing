# SUT B — Інтернет-магазин

Java 21, Maven, PostgreSQL 17, JDBC, JUnit 5 та Mockito. Варіант 14: базовий магазин із персональним правилом знижки.

## Поведінка

- Товар має унікальний непорожній артикул до 40 символів, ціну 100–1 000 000 копійок, невід’ємний залишок та ознаку акційності.
- Замовлення містить одну позицію одного товару. Кількість — 1–20 включно; код замовлення — унікальний непорожній рядок до 40 символів. Ідентифікатор товару додатний.
- Оформлення перевіряє наявність товару та достатність залишку. Потім один раз викликає зовнішній дозвіл `OrderPolicy.isAllowed(product, quantity)`. Відмова або виняток припиняє оформлення без запису.
- Сума — ціна × кількість мінус знижка, у цілих копійках, без доплат. Преміальність і підтвердженість купона зберігаються в замовленні.
- Успішне оформлення зберігає замовлення CONFIRMED і позицію з ціною та акційністю на момент покупки. Подальші зміни товару не змінюють замовлення.
- Повернення змінює CONFIRMED на RETURNED. Повторне повернення заборонене. Обмежень за днями, пакуванням або акційністю поки немає. Зовнішній дозвіл при поверненні не викликається.
- Оформлення й повернення не змінюють залишок товару.

## Персональна функція: розрахунок знижки

15% за підтвердженим купоном; інакше 10% від 1600 грн. Знижки не додаються.

Усі пороги включні й визначаються за сумою до знижки. Сума знижки округлюється донизу до цілої копійки та віднімається один раз. Якщо жодна умова не виконується, знижка становить 0%. Ознаки, не згадані в правилі, на знижку не впливають. Загальний ліміт кількості 1–20 та базове повернення залишаються без змін.

`couponValid` — вхідна ознака вже підтвердженого купона; перевірка кодів купонів не входить до цієї системи. Акційність береться з товару, преміальність — із заявки.

## API

`OrderService(products, orders, policy)`:

- `calculateTotal(unitPrice, quantity, premium, couponValid, onSale)` — розрахунок суми за персональним правилом; коротка форма з двома аргументами використовує false для всіх ознак;
- `placeOrder(new OrderRequest(reference, productId, quantity, premium, couponValid))` — оформлення з персональною знижкою; конструктор без couponValid використовує false;
- `returnOrder(id)` — повернення.

Некоректні входи та відсутні товари/замовлення — `IllegalArgumentException`; бізнес-відмови — `OrderRejectedException`. Помилки БД передаються як `SQLException`.

`ProductRepository(connection)`: create, findById, update, delete.
`OrderRepository(connection)`: create, findById, findAll, findOrders(productId, status), updateStatus, delete.

create повертає збережену модель з ідентифікаторами БД; вхідні id ігноруються. findById повертає null за відсутності запису. findOrders застосовує обидві умови одночасно. Списки впорядковані за id. Оновлення відсутнього запису викликає IllegalArgumentException, видалення — нічого не змінює. Видалення замовлення каскадно видаляє позицію; товар із позиціями видалити не можна. Обмеження таблиць перевіряє PostgreSQL.

Репозиторії отримують відкрите JDBC-з’єднання; власник закриває його через try-with-resources. Створення замовлення та позиції виконується атомарно. Для create потрібен autoCommit=true; не запускайте паралельні операції на цьому з’єднанні та не обгортайте create у зовнішню транзакцію. OrderPolicy передається як Stub/Mock або лямбда; реальних зовнішніх інтеграцій немає.

## Запуск

Створіть навчального користувача та окрему тестову БД у локальній PostgreSQL:

```sql
CREATE ROLE store_student LOGIN;
\password store_student
CREATE DATABASE store_variant14_test OWNER store_student;
```

Із папки sut-b застосуйте міграції один раз до нової БД:

```sh
psql -h localhost -U store_student -d store_variant14_test -v ON_ERROR_STOP=1 -f migrations/V1__create_tables.sql
psql -h localhost -U store_student -d store_variant14_test -v ON_ERROR_STOP=1 -f migrations/V2__add_indexes.sql
```

Налаштуйте змінні середовища за `.env.example`; файл .env автоматично не читається. Пароль задайте через DB_PASSWORD.

```sh
mvn compile
mvn test
```

Наявний тест перевіряє лише підключення до БД. Таблиці спочатку порожні; дані для сценаріїв готуйте у власних тестах. Схеми та дані автоматично не створюються й не очищаються при запуску тестів. Для незалежності тестів очищайте власні замовлення перед товарами або використовуйте окрему тестову схему.
